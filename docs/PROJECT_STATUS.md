## What this project is
AI-powered personal to-do app. Captures tasks (text/voice/image), auto-categorizes and prioritizes them with Gemini, sends push reminders, syncs two-way with Google Calendar, has an AI agent that answers questions about your tasks AND can propose task changes (complete/update/create) via confirmation cards — see below. Backs a real Airbnb/Hostaway short-let business (Hostaway guest messages become tasks automatically). Multi-user and production-deployed.

**Recurring tasks, Slice 1 — walked through in a browser and it worked (2026-08-17).** Backend suite at 209 (was 106 before this plan started), frontend build clean, ESLint at its pre-existing baseline of 13 (**13 as of that date; 12 since 2026-08-25**, one of them fixed by the calendar pass), zero `eslint-disable` anywhere. Design in `docs/superpowers/specs/2026-08-15-recurring-tasks-design.md`, plan in `docs/superpowers/plans/2026-08-15-recurring-tasks.md`.

A recurrence is a weekly (a set of weekdays) or monthly (a day of the month, or -1 for "last day") rule in a new `recurrence_rules` table, materializing a rolling ~14-day window of REAL rows in `tasks` — not a virtual computation, not a flagged template row — so Today, Upcoming, the calendar grid, the daily summary, calendar sync and the agent's day view/`search_tasks` all see occurrences with zero code change to any of them; this was the single largest saving the design banked on, and it is why the generator itself is a small pure module (`recurrence.py`, no I/O, the same shape as `hostaway_threading.py`). `occurrence_date` is deliberately its own column, separate from `due_date`, so dragging an occurrence to another day does not make the next tick recreate the original as "missing" — `UNIQUE (recurrence_rule_id, occurrence_date)` is the real duplicate guard, in the database rather than in Python, because the ~2-minute scheduler tick has to survive a crash, a retry or an overlapping run unscathed. A missed occurrence gets one day of grace, then `missed_at` (its own column, not `is_rejected` — reusing that would have corrupted the AI-learning signal that flag exists to carry) and leaves the visible lists on its own, without being deleted. A single deleted occurrence now stays deleted (`cancelled_at`, an owner decision made mid-plan) instead of the hard-delete it replaces, which the generator used to silently recreate within about two minutes. Settings gained a "Recurrences" screen (list, on/off switch, New/Edit form) and every generated task carries a ↻ badge back to its rule.

Later the same day, the second half of that sentence grew teeth: **a task can now be made to repeat from the task itself** — the ⋯ menu and a "Repeat" row in the detail sheet — and the badge became a button that opens the rule. The interesting part is not the UI but what happens to the task the user was looking at: `POST /recurrences` takes an optional `adopt_task_id` and the named task BECOMES the rule's first occurrence (given `recurrence_rule_id` and `occurrence_date`, adopted before materialization, so the generator's existing skip-what-is-already-on-disk rule prevents the twin). Adoption links and does not edit — the rule's time and priority are not written over the task's. A task already owned by a rule is a 422 and a task that is not yours a 404, both resolved before the rule row is written, so a failed adoption cannot strand an orphan rule that fires every morning with no screen admitting it exists.

**Two migrations, both applied by the owner and verified by him reading the query output, not assumed**: `recurrence_rules` (2026-08-15) and `tasks.cancelled_at` (2026-08-16).

**The sharpest defect, found by the implementer reading, not by any test**: `create_task_manual` built its `TaskRecord` field-by-field and never carried `recurrence_rule_id`/`occurrence_date`, so a generated occurrence would have written NULL into both — every test for this path monkeypatched `create_task_manual`, so the suite was structurally blind to the exact seam the bug lived on. Had it shipped: `get_occurrence_dates` would have matched nothing against those NULLs, the set difference would always read "the whole window is missing", `UNIQUE (recurrence_rule_id, occurrence_date)` cannot fire because Postgres treats NULLs as distinct, and the ~2-minute cron would have inserted roughly 11 tasks every tick — about 8.000 a day into a real business's task list. Caught and fixed before any deploy.

**A CHECK constraint that did not check**: the migration's own comment claimed a weekly rule with no weekdays was rejected. `array_length('{}', 1)` returns NULL, not 0, and a CHECK only rejects on an explicit FALSE — so the constraint accepted precisely the row it was written to forbid, silently. Caught in review before the SQL ever reached the owner; fixed to `cardinality(weekdays) > 0`.

**The same root cause, three separate times in this plan**: one value made to carry two facts, and the failure case losing the distinction. `recurrences_missed = 0` meant both "looked, found nothing" and "did not look". PATCH's None-filter erased "field not sent" versus "field sent as null". And `get_task` returning `None` meant both "no such row" and "the lookup itself failed" — which would have hard-deleted a recurring occurrence on a transient database blip, and the generator would have resurrected it within two minutes. All three fixed by giving the two facts separate representations rather than by patching the symptom.

**Hostaway became per-user (2026-08-14).** Implemented and committed on `main`; 102 unit tests pass. Design in `docs/superpowers/specs/2026-08-13-hostaway-per-user-integration-design.md`, plan in `docs/superpowers/plans/2026-08-13-hostaway-per-user-integration.md`.

Any user can connect their own Hostaway account from Settings → Hostaway. Credentials travel as an argument into every Hostaway call instead of living in two module globals read from `.env`; the access-token cache is keyed by account, because a single global would have handed one user's token to another user's requests the moment a second account connected. Secrets are stored as Fernet ciphertext (`crypto.py`, `HOSTAWAY_ENCRYPTION_KEY`), and `get_user_id_for_hostaway_account()` — which returned the owner's user_id hardcoded — is deleted.

**What is verified, and by what:**
- **`POST` and `DELETE /v1/webhooks/unifiedWebhooks` work.** Called once against the live account 147809 on 2026-08-14 with the owner's go-ahead: POST returns 200 with the new id at `result.id`, DELETE returns 200 with an empty `result` list. Only `GET` had ever been called before, and Task 7 of the plan was built entirely on this. The throwaway webhook was deleted and a follow-up listing showed only the four known ones.
- **The owner's own connection works end to end.** `migrate_owner_hostaway.py` wrote his row (account 147809, claiming the webhook 34986 he already had), and a poller dry run then resolved credentials *out of that row* instead of `.env`, polled two conversations and wrote nothing.
- **102 unit tests**, including three that hold the cost line: one guest message means one classification and one pair of enrichment calls no matter how many colleagues are connected, and an account nobody has connected costs no Gemini call at all.

**Two defects found by reading after the push, both since fixed** (CURRENT_TASK.md, Gap 0): a missing or wrong `HOSTAWAY_ENCRYPTION_KEY` made the webhook return **500 instead of its contractual 200** — which is how Hostaway disables a webhook, turning a temporary misconfiguration into a permanent outage — and made **one user's failure kill the whole scheduler tick for every other user**, because the per-user loop had no exception guard. `crypto.py` promises a missing key breaks only Hostaway paths; it was breaking reminders, daily summary, escalations and calendar sync for everyone. Both fixed with tests that failed first (106 tests now).

**Hostaway threading, a conversation link, and auto-complete on reply (2026-08-10).** Implemented and committed on `main`; unit-tested; **never exercised against a real webhook delivery** — see CURRENT_TASK.md. Design in `docs/superpowers/specs/2026-08-10-hostaway-threading-design.md`, plan in `docs/superpowers/plans/2026-08-10-hostaway-threading.md`.
A Hostaway task now means "this conversation is waiting for me" rather than "a message arrived", and all three requested behaviours fall out of that one redefinition. Burst messages within **90 seconds** fold into one task; the task links to its Hostaway conversation; a human reply completes it (P3 only — see FEATURES.md; this line read "P2/P3" until 2026-08-23 and never matched the code) or silences it (every other priority).
**The whole design keeps the AI out of every decision** — a timestamp comparison, a null check and a priority rank, all in a new `hostaway_threading.py` with no I/O. This was the stated requirement («σε όλα αυτά θέλω zero fail, όχι 9/10») and it is only achievable because "is this the same conversation?" and "did a human write this?" are facts Hostaway already records, unlike "is this the same topic?", which is a judgement and was refused.
**The API was probed before anything was designed, and it earned it:**
- The account runs a `messageReceived` automation — *"we received your message and will reply shortly"* — that fires after EVERY guest message. The obvious auto-complete would have **closed every task within seconds of creating it, silently.** Same shape as the `delete_calendar_event` bug: a success path nobody checked.
- The signal that survives is **`userId`** (null on all 66 automations, set on 23 of 24 human replies), NOT `communicationId` — a third-party **GuestArrive** message has neither field and would have passed as a human reply.
- The **90-second window is measured**: 141 real message pairs, every burst under 42 s, nothing between 1 and 2 minutes, two genuinely different problems at 2.4 minutes («den exv mpataria» → «δεν εχω νερο»).
- `conversationId` is on every message and the deep link is `dashboard.hostaway.com/messages/inbox/{conversationId}`, confirmed against a real URL.
- **`get_reservation_details` guessed right.** `guestName`/`arrivalDate`/`departureDate` are real; the day-one warning is deleted, along with the log line it asked for, which was dumping `guestEmail`, `phone` and `ccNumberEndingDigits` into the application log on every guest message.
**This repo now has automated tests** — 34 of them, first ever, in `tests/` with pytest in a standalone `requirements-dev.txt` (`requirements.txt` is UTF-16LE and ships to Render). The measured message pairs and the three real outgoing payloads ARE the test cases.
**ANSWERED (2026-08-12): Hostaway does NOT deliver outgoing messages, and the trigger moved to the scheduler.** The owner reported replying to a guest with nothing happening. Three independent pieces of evidence:
- The app's own webhook (id 34986) is subscribed to `message.received` and Hostaway only delivers what you subscribe to. The account's three other webhooks (Make, Zapier, GuestArrive) each enumerate the *same five* events — `reservation.created/updated`, `message.received`, `task.created/updated` — which is what "subscribe to everything" looks like, and none of them covers a sent message. GuestArrive is a guest-messaging product; if such an event existed it would be on that list.
- **`hostaway_answered_at` was null on all 15 Hostaway tasks ever written**, including completed ones — and the code writes it in the SAME dict as `is_completed`. So every task that looked auto-completed was closed by hand: the outgoing path had never run once since it shipped.
- Three real human replies were sitting in `GET /v1/conversations/{id}/messages` the whole time, including one at 07:51 that day.

**The webhook's own diagnostic had a hole**, which is why this went unnoticed: `[hostaway webhook] Outgoing message:` only logs once the `event == "message.received"` check has passed, and the unmatched-event branch returned **silently**. "No line in the log" could not distinguish "Hostaway never called" from "Hostaway called with an event name we don't match", and Gap A was going to be settled on exactly that silence. Every delivery now logs its event name *before* any filtering (`[hostaway webhook] Delivery:`), with tests that fail without it.

**The fix is `TaskService._check_hostaway_replies`**, on the existing ~2-minute cron: one `GET /v1/conversations/{id}/messages` per conversation with an open task, then the same pure decisions as before. `find_unanswered_human_reply` adds one rule the webhook never needed — the reply must be **newer than the guest message the task is about**. Conversation 44234683 is why: a guest wrote at 06:23 and the newest human reply was 17:21 the *previous day*, so "does this conversation contain a human reply?" would have closed a brand-new task on sight. **Auto-completion is staged: `HOSTAWAY_REPLY_AUTOCOMPLETE_PRIORITIES = {"P3"}`** — the least urgent priority only, until the owner has watched it work («για αρχή, μην χάσω κανένα τασκ»). A P1 or P2 reply records `hostaway_answered_at` and stops the escalation nagging, but the task stays on the list for a human to close. Adding `"P2"` to that set is the whole change; both reply paths read it. P1 is never a candidate.

**VERIFIED RUNNING (2026-08-13, `cd5187e`)**, watched against the `tasks` table rather than trusted: one task closed on the first tick after deploy from a reply sent hours earlier, and a second — which the dry run had correctly left alone half an hour before, because it had no reply yet — was closed within ~2 minutes of its reply actually being sent. Detection and restraint on the same task, half an hour apart. What is still unobserved is in CURRENT_TASK.md, Gap A2: the escalation not firing in a discovery tick, the ambiguity push, and a P1/P2 reply recorded without completing.

**Measured over the following ten days (2026-08-13 → 08-23, 39 Hostaway tasks), after the owner reported that replying had "stopped closing tasks".** It had not stopped: **detection is exact** — every human reply that landed while its task was open was recorded, and each task without a `hostaway_answered_at` either never received a human reply or had been closed by hand *before* the reply arrived (119 minutes before in one case, 47 hours in another). Zero misses. **Completion is the narrow part**: 8 of the 27 detected replies closed their task. Of the 19 that did not, **11 were blocked by the ambiguity rule and 6 by P3-only staging** (2 predate the poller's deploy). The ambiguity rule compounds, and that is the part worth knowing: nothing closes what it blocks, so open tasks accumulate in a conversation — 47691626 and 45902159 each reached **7** — and past two, no reply in that conversation can auto-close anything again. **Both gates were reviewed by the owner on 2026-08-23 and deliberately KEPT** (see DECISIONS.md). Nothing in the code changed; two docs that claimed "P2/P3" were corrected to match the code, which has said P3 only since `cd5187e`.

**A second agent: natural-language editing on the task card itself (2026-08-07).** `task_agent.py` + `POST /tasks/{record_id}/agent-edit` + an input row inside the expanded `TaskCard`. Open a task, type "βάλ' το Παρασκευή απόγευμα", and it edits that task.
The point is what it does NOT contain. Almost all of the chat agent is there to work out WHICH task is meant — `search_tasks` and its fallback tiers, the day view, conversation memory, the refs block, and both anti-wrong-task guards. Here the `record_id` is the card the user is looking at, so none of that has anything to protect, which also means **no tools**: one structured-output call, always one round, no `MAX_TOOL_ROUNDS`, and none of the round-count cost the token audit identified as the chat agent's entire cost driver. ~1.100-token fixed prefix against 2.729. See DECISIONS.md for why this is a second agent rather than a narrower prompt on the first.
It **plans; the app writes** — the endpoint returns a validated diff and `TaskCard` applies it through the same `onUpdate` its manual Save uses, so agent edits and hand edits share one write path and the reminder/calendar/delete-reporting logic on it stays untouched. Changes apply immediately with an UNDO toast (`before` computed server-side); delete is the one exception and always confirms, reusing the card's existing delete flow. It can change dates, times, name, description, priority, category, done-state, checklist, and the reminder/calendar toggles; it cannot approve or reject a task.
**Measured against the real model**: 22-case Greek+English suite, every case twice — **22/22 correct on both runs** (relative dates, parts of the day, clearing, three fields in one instruction, checklist append, ambiguity answered with a question instead of a guess, "τελείωσα με αυτό" completing rather than deleting, and a prompt-injection description treated as text). **Median 860 tokens and $0,00028 per edit** — the chat agent is 7.444 tokens/run, so ~8,6× cheaper, which is exactly what no tools and one round buys. Offline underneath: 10 hand-built plans through the normaliser, all five actions plus 404/422/503 via `TestClient`, schema conversion, `{"due_time": null}` surviving `exclude_unset=True`, clean build, no new ESLint violations.
**Two bugs the suite caught**, both fixed: a reminder was being enabled on a task with no time (the server guard dropped it correctly, but the message claimed success — it now asks for the time), and the message came back in the wrong language. The second is the interesting one: **it could not be fixed by prompting at all.** The model follows the language of the DATA, and every task here is Greek; the rule was in the FIRST line of an instruction a twentieth the size of the chat agent's and still lost, while strengthening it flipped every Greek answer to English. It is now decided in code (`answer_language()` reads the instruction's script, the prompt states the language as a fact) — 22/22 both ways after. **This refutes the standing explanation for the chat agent's own Gap 3**, which blamed last-line placement and proposed moving the line up; that fix should not be tried, the code-side one should. See DECISIONS.md.
**Confirmed working in the real app** by the owner, who then asked for the UI: it worked, but the control was a bare text box between two form sections with nothing saying it was a feature. Rebuilt as a labelled ✨ panel — heading, spinner + "Το επεξεργάζομαι…", state-derived suggestion chips while the box is empty, and a per-field `before → after` list of what changed. Chips are deliberately all rescheduling; priority/completion/reminder chips were built and cut, because they would spend a model call on what the dropdown, the ○ button and the bell already do in one free tap (the "add a task" chip reasoning from DECISIONS.md). The toast keeps the UNDO because it outlives the card; the panel keeps the detail, which the toast has no room for.
**Editing a pending task now approves it** (same day, on request): Save on an Inbox task sends `approval_status: true` with the field changes, and so does an inline agent edit — reviewing a task and confirming a change to it IS the approval, and the ○ already worked this way when completing one. Announced, never silent (the button reads "Αποθήκευση & Έγκριση", the toasts say so), UNDO puts the task back in the Inbox, and rejected tasks are excluded — rejecting leaves `approval_status` false, so without that guard any edit would have silently approved them. **Google Calendar: a silent failure, a silent success, and a grid that picked the wrong thing (2026-08-07, `f4dca15`..`1eb15c5`, on `main`).** Three commits, all from real reported use, none of them agent work.
- **The bug**: `delete_calendar_event` was the only Google API call in `google_calendar.py` that never called `raise_for_status()`. `requests.delete()` doesn't raise on a 401/403 — it returns normally — so the `try` completed, the `except` never ran, nothing was logged, and the app believed the event was deleted while it was still on the user's calendar. This explains the reported symptom exactly: tasks deleted in the app whose Google events stayed behind, with no error anywhere. Now checked, with 404/410 treated as success (the event is already gone, which is the outcome the function exists to produce). **Failures are now visible; they are not retried, and events already orphaned by the silent version are still out there** (see BACKLOG.md).
- **The silence**: the origin-aware deletion rule was correct — an app-origin task's event is deleted with it, a task converted FROM a Google event keeps that event, because the app doesn't own it — but nobody was told. `DELETE /tasks/{id}` returned 204 No Content, so all four outcomes rendered as the same one-word "Deleted" toast. It now returns 200 with `{"calendar": "none" | "deleted" | "kept_google_origin" | "delete_failed"}`; the UI shows a longer neutral toast for `kept_google_origin` saying WHY the event is still there and where to remove it, an error toast for `delete_failed`. `api.js` tolerates a body-less response, so a frontend deployed ahead of the backend keeps working. The task is deleted in all four cases — reporting, not a behaviour change.
- **The grid**: month-cell event chips used to `stopPropagation` and jump straight to Google, so a day with two events opened whichever one your finger landed on and the DAY only opened if you managed to miss both. Chips are now inert previews and the whole cell selects the day, matching the task chips that already behaved that way. And "Make it a task" existed only in the Today view, so an event on any other date could be seen but not acted on — the day popup now carries the same make-task/dismiss buttons, wired to `convertCalendarEventToTask`/`dismissCalendarEvent`, which were already in `api.js` with no caller here.

**The calendar week starts on Monday, and dates are named in the user's language (2026-08-25).** Owner-reported, three files, no backend change.
