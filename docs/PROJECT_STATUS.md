## What this project is
AI-powered personal to-do app. Captures tasks (text/voice/image), auto-categorizes and prioritizes them with Gemini, sends push reminders, syncs two-way with Google Calendar, has an AI agent that answers questions about your tasks AND can propose task changes (complete/update/create) via confirmation cards — see below. Backs a real Airbnb/Hostaway short-let business (Hostaway guest messages become tasks automatically). Multi-user and production-deployed.

Manually verified end-to-end while logged in against live Supabase data.
- **Agent read-path correctness + failure modes (PR A)**: per-round/per-run token instrumentation is deployed (log-only, `token_usage_log` unchanged) and showed the entire cost driver is the number of tool rounds, with the worst profile (a mis-resolved weekday) ending in a user-visible error. Fixed: a single `is_open_task()` predicate replacing duplicated inline filter logic; one clock read per request (was two) feeding the system instruction, search_tasks, and an injected `[Now:]`/`[Next 7 days]` header; weekday names now resolved by table lookup instead of model arithmetic; "overdue" corrected to strictly-before-today in both places it was stated; `no_matches_hint` to stop blind adjacent-date retries; the round ceiling (`MAX_TOOL_ROUNDS`, now 4, was 6) degrades to a real answer (`outcome=max_rounds_recovered`) instead of raising. A follow-up (measured on real production logs) also fixed the agent inventing category/priority/date filters the user never asked for.
- **Agent day view**: measured baseline showed every question costs exactly 2 rounds (~3,350 tokens each, ~7,000 total; write requests 3 rounds, ~10,700) and the round count is the entire cost driver. `agent_tools.build_day_view()` now pre-loads overdue + today's open tasks (plus anything pending approval due today/late, in its own section) into the FIRST user turn, unconditionally, every request — so day-scoped questions resolve in one round instead of two: measured ~7,000 → ~3,600 tokens for reads, ~10,700 → ~7,100 for writes on today's tasks. All three sections are capped (overdue 10, today 15, pending 5) with an overflow line, since the day view sits in `contents[0]` and is re-sent every round. This REPLACES the earlier `overdue_count` mechanism (removed — two mechanisms answering the same question is exactly the bug shape the invented-filters fix had to correct). A day-view row's `record_id` is now also a valid write-proposal source, alongside a tool result. Verified end-to-end — see the next entry.
- **Agent day view verified + instruction compressed (2026-08-02)**: the whole acceptance list was run end-to-end against real data by calling `ask_agent()` in-process (no frontend/login needed — see CURRENT_TASK.md for the method). Day view confirmed working: day-scoped questions resolve in 1 round with no tool call; tomorrow/this-week/weekday correctly still force `search_tasks`. **Discovered there is no implicit caching on this model** (three identical calls, `cached=0`, no cache field in `usage_metadata`), which killed a planned "static system instruction" change and made prefix size the only cost lever. System instruction then compressed 40% (2.473 → 1.490 tokens), cutting the fixed per-round prefix 3.712 → 2.729 and **total tokens -23% on every test**, with zero behavioural regression. Two production bugs found and fixed in the process: invented date/category filters on the write path, and `include_completed` never being used (an already-completed task was reported as "not found" — wrong answer at 13.017 tokens; now correct at 6.545).
