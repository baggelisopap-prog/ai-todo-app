# ARCHITECTURE — stack, files, deployment, constants
_Single source of truth for the technical shape. Verify against real code when Claude Code bootstraps this; the code wins on any discrepancy._

## Stack
- **Backend**: FastAPI (Python) + Supabase (PostgreSQL) + Google Gemini. Fully migrated OFF Airtable (Airtable kept only as a read-only legacy backup).
- **Frontend**: React + Vite + Tailwind CSS + react-i18next (i18n: English + Greek, both fully translated) + @supabase/supabase-js.
  **CORRECTED**: an earlier draft said "Greek default + English". Verified against `frontend/src/i18n.js`: the default/fallback language is `en`; Greek (`el`) is a full, complete translation the user switches to manually via Settings → Language, and the choice persists in `localStorage` (`app_language`). There is no server-side or browser-locale-based Greek default.

## Backend files and responsibilities
- **main.py** — all FastAPI endpoints; `get_current_user_id` auth dependency (verifies the bearer token via `supabase.auth.get_user(token)`). Endpoint areas: tasks CRUD (`/tasks` GET/POST, `/tasks/{id}` PATCH/DELETE), extract (`/extract`, `/extract-voice`, `/extract-image`), agent (`/agent/query` — accepts an optional `conversation_id` and always returns one, see FEATURES.md's "AI agent (memory)" section; `/agent/confirm-action` — see FEATURES.md's "AI agent (write)" section), settings (`/settings` GET/PATCH), calendar (`/calendar/connect`, `/status`, `/disconnect`, `/test`, `/events`, `/events/{id}/convert`, `/events/{id}/dismiss`), profile/account (`/profile` GET/PATCH, `/account` DELETE), Hostaway webhook (`/webhooks/hostaway`), scheduler (`/notifications/run-scheduler`), dev (`/dev/token-usage`), `/health`. `/agent/confirm-action` re-validates every agent-proposed write from scratch server-side (type, field whitelist, enum/date/time values, user_id scoping) — it is the security boundary, never trusting the proposal the frontend echoes back.
- **repository.py** — ALL Supabase CRUD. Every function is scoped by `user_id` (except `get_all_tasks_for_scheduler`-style enumerations used by the per-user scheduler loop, which are intentionally global). App-code `user_id` filtering is the PRIMARY security boundary because the secret key bypasses RLS. `get_recent_agent_runs(user_id, conversation_id, limit)` (selects `id, question, answer, refs` from `agent_runs` where `answer` is not null, never raises — returns `[]` on any failure, reversed into oldest-to-newest order) and `log_agent_run(user_id, payload)` (writes one row to `agent_runs`, building the insert dict explicitly from a fixed column whitelist `_AGENT_RUN_COLUMNS` rather than splatting `payload`, and — unlike most functions in this file — never raises: any failure is caught and logged) both operate on the SAME `agent_runs` table — see FEATURES.md's "AI agent (memory)" and "Developer diagnostics", and DATABASE_SCHEMA.md. One row is one question/answer pair, so it serves as both the bounded agent conversation memory and the developer diagnostic archive; there is no separate messages table (`save_agent_message`/`get_recent_agent_messages` and the `agent_messages` table they targeted have been removed — see DECISIONS.md).
- **services.py** — TaskService; push sending (`send_push_to_user(user_id, ...)`); `run_notification_scheduler()` which loops every active user via `get_all_active_user_ids()`; Hostaway escalations; `sync_google_calendar_for_user(user_id)`. `create_task_manual(user_id, fields, approval_status=True)` — the `approval_status` param defaults `True` for the normal manual-create path (`POST /tasks`) and is passed `False` by `/agent/confirm-action` so an agent-created task lands in the Inbox for approval instead of the task list.
- **agent_engine.py** — Q&A + propose-then-confirm write AI agent. Manual tool-call loop against google-genai with Automatic Function Calling DISABLED (so token usage can be summed across every round — AFC undercounted). `ask_agent(question, user_id, conversation_id=None) -> {"answer": str, "proposed_actions": list[dict], "conversation_id": str}` loads that user's tasks into RAM, exposes the read tools (`search_tasks`, `get_task_details`) plus the write-proposal tools (`propose_complete_task`, `propose_update_task`, `propose_create_task`) from `agent_tools.build_write_proposal_tools`, and returns the answer, whatever proposals were registered during the tool-calling loop, and `conversation_id`. The propose_* tools never write to the database themselves — see FEATURES.md. Whether `conversation_id` was actually passed in is captured BEFORE a missing one is minted (`uuid4`) — a brand-new conversation has no history to load, so the history read is skipped entirely rather than wasting a query; otherwise `repository.get_recent_agent_runs(user_id, conversation_id, limit=agent_tools.HISTORY_MAX_PAIRS)` loads that conversation's last 4 runs (wrapped in try/except — a history-load failure falls back to `[]` and never blocks the answer), and `agent_tools.build_history_contents` turns them into `contents` entries PREPENDED before the current turn (two per run: the stored question, then the stored answer). The LATEST (current) user turn — never an earlier, replayed one — carries the `[Now:]`/`[Next 7 days]` time header PLUS `agent_tools.build_day_view(cached_tasks, today_iso, now_hhmm)` — a pre-rendered overdue+today (+pending-approval) view — so day-scope questions can resolve in a single round with zero tool calls; a `[agent] day_view injected: N rows` log line records its size every request. After the tool-calling loop ends, the distinct `record_id`s surfaced by `search_tasks`/`get_task_details` results THIS run (not the day view, which is re-injected fresh every request and never needs remembering) become `refs`, capped at `agent_tools.HISTORY_MAX_REFS` (5) — a run touching more tasks than that stores `refs=[]` rather than an arbitrary subset. The question and answer (with its refs) are recorded onto the in-progress `run` dict — see below — rather than written immediately; the single write in the `finally` block is what persists them. A `[agent] history: {n} messages replayed, {r} refs stored` log line, and an added `history={n}` field on the existing `[agent][SUMMARY]` line, record this every request. The loop logs a `[agent][round N]` line per round (prompt/output/thinking/cached/total tokens plus which tools were called) and a `[agent][SUMMARY]` line per run covering every exit path including failures (`ok`/`no_answer`/`max_rounds`/`api_failure`/`max_rounds_recovered`) — this is log-only instrumentation for the ongoing token-cost investigation (see DECISIONS.md); `token_usage_log` writes via `token_tracker.log_token_usage()` are unchanged. `MAX_TOOL_ROUNDS` is now `4` (was `6`): hitting the ceiling no longer raises — one final tool-less `generate_content` call forces an answer from whatever was already found (system instruction unchanged, no `tools` passed so it cannot call anything), logged as `outcome=max_rounds_recovered`; only a genuinely empty final answer still raises. At the very top, `agent_tools.strip_test_label(question)` strips an optional `#label ` prefix (e.g. `#t3 `) before the question touches the prompt, history, or persistence — the model never sees it; the original is kept as `raw_question` for diagnostics. The whole function body runs inside a `try/except/finally`: a `run` dict is accumulated as the loop proceeds (the exact first-turn text, `agent_tools.system_instruction_sha` of the system instruction actually passed, day-view row count, history message count, a `rounds_detail` JSON array with one entry per round — tokens, `finish_reason`, and every tool call's name/args/result — plus the same totals/outcome already in the `[SUMMARY]` line, `latency_ms`, and `error` on a failure path), and `repository.log_agent_run(user_id, run)` writes it in the `finally` block, so a run that RAISES is still recorded with its outcome and error — this is developer-tooling instrumentation only (see DATABASE_SCHEMA.md's `agent_runs`, DECISIONS.md), fully separate from the `token_usage_log` figures above and from the response returned to the caller. A `[agent] run logged: outcome=<outcome> rounds=<n>` line is added after the write; every other console log line is unchanged.
- **agent_tools.py** — shared system instruction builder + read-tool factory (`search_tasks`, `get_task_details`) + write-proposal tool factory (`build_write_proposal_tools(proposed_actions, available_tasks)` → `propose_complete_task`/`propose_update_task`/`propose_create_task`) + `AGENT_WRITABLE_FIELDS` (the field whitelist `main.py`'s `/agent/confirm-action` re-checks against) + Greek→Latin transliteration for fuzzy keyword matching. `is_open_task(t, include_completed=False)` is the SINGLE SOURCE OF TRUTH for "counts as an open task" (not rejected, approved, not completed unless asked) — every open-task filter in the module (the main `search_tasks` loop, the `no_matches_hint` lookup, `build_day_view`'s overdue/today sections) routes through it. `is_pending_task(t)` is the parallel single source of truth for "awaiting approval in the Inbox" (not rejected, not completed, `approval_status` false) — deliberately NOT "open", but surfaced separately in the day view so an escalating Hostaway task due today isn't invisible. `PRIORITY_ORDER` ranks P1/P2/P3 for sorting. `build_time_context()` does the module's ONE clock read per request, returning `(today_iso, now_hhmm, header)`. `build_day_view(tasks, today_iso, now_hhmm)` renders the compact OVERDUE/TODAY/PENDING APPROVAL view described in FEATURES.md, using `DAY_VIEW_DESC_LENGTH` (70), `DAY_VIEW_OVERDUE_CAP` (10), `DAY_VIEW_TODAY_CAP` (15), and `DAY_VIEW_PENDING_CAP` (5) — all three sections are capped with a "(+N more ...)" overflow line, since the day view sits in `contents[0]` and is therefore re-sent on every round. `build_system_instruction(today_iso, now_hhmm)` and `build_tool_functions(cached_tasks)` take their date/time from `build_time_context`'s resolved values (or don't need it at all, in `build_tool_functions`'s case, since `search_tasks` no longer computes an overdue count itself) instead of reading the clock themselves. `search_tasks` no longer returns `overdue_count` — the day view replaced it (see DECISIONS.md). `HISTORY_MAX_PAIRS` (4), `HISTORY_MSG_MAX_CHARS` (500) and `HISTORY_MAX_REFS` (5) bound the conversation-memory feature (see FEATURES.md/DECISIONS.md); `build_history_contents(runs)` maps `agent_runs` rows (oldest→newest, as returned by `repository.get_recent_agent_runs`) into google-genai content dicts — each run becomes TWO entries, a "user" turn from `question` then a "model" turn from `answer` — truncating each independently to `HISTORY_MSG_MAX_CHARS` and appending a compact `[refs: name=id; ...]` line (capped at `HISTORY_MAX_REFS`) to the answer turn when the run has refs. `strip_test_label(question)` recognizes a `#label ` prefix (1-20 chars of `[A-Za-z0-9_-]` then required whitespace) used to tag a manual test run for later lookup in `agent_runs`, returning `(clean_question, label_or_None)` — the model must never see the label. `system_instruction_sha(text)` returns the first 12 hex chars of the text's sha256, a short fingerprint identifying which prompt version produced a given `agent_runs` row across deploys. Holds the system-instruction directives: CONFIDENTIALITY, DATA VS INSTRUCTIONS (now also explicitly covers conversation history, not just tool results/the day view), PRE-LOADED DAY VIEW, FILTERS, DATE RESOLUTION, RESULTS, CONVERSATION HISTORY (replaces the old SINGLE SELF-CONTAINED QUESTION directive, which flatly denied any history existed — now false), WRITE ACTIONS, TIME AWARENESS. **Measured cost (2026-08-02): the instruction is 1.490 tokens and the full fixed prefix 2.729 tokens, paid on every round** — there is no implicit caching on this model (see DECISIONS.md), so prefix size is the only cost lever and new rules must go INSIDE an existing section rather than be appended as a new one.
- **ai_engine.py** — Gemini extraction from text/voice/image into structured task data.
- **hostaway_integration.py** — Hostaway webhook AI classification, OAuth callback, enrichment, and `get_user_id_for_hostaway_account()` (the "one door": currently hardcoded to the owner user_id; the ONLY function to change when multiple users connect their own Hostaway later).
- **google_calendar.py** — per-user Google token management (`get_valid_access_token`), `sync_task_to_google_calendar`, `pull_calendar_changes`, `test_calendar_connection`, `delete_calendar_event`, `mark_event_completed`.
  **CORRECTED**: an earlier draft described `get_valid_access_token` as doing a "proactive 5-min-buffer refresh via `_refresh_access_token`". Verified against the actual code: there is no separate `_refresh_access_token` helper, and the refresh is REACTIVE, not proactive — it only refreshes when `datetime.now(timezone.utc) >= expiry` (i.e. after the token has already expired), with no buffer margin. Same correction applies to DECISIONS.md and PROJECT_STATUS.md.
- **token_tracker.py** — per-user, per-model cost logging (`log_token_usage(..., user_id)`, `get_usage_summary(user_id)`).
- **migrate_to_supabase.py** — one-off Airtable→Supabase migration script (reads raw Airtable REST API). Historical; kept for reference.

## Frontend shape
- Views: Inbox / Today / Upcoming / Calendar (Monthly + Weekly) / Browse, plus the agent chat and Settings modal.
- `api.js` wraps all backend calls with an authenticated fetch (bearer token from the Supabase session). `askAgent(question, conversationId)` sends `conversation_id` in the body only when set, and returns the full `{answer, proposed_actions, conversation_id}` object (not just the answer string); `confirmAgentAction(action)` posts one proposed action to `/agent/confirm-action` and returns `{status, message, task}`.
- `AgentChatModal.jsx` renders one confirmation card per proposed action directly under the assistant reply it came from — see FEATURES.md's "AI agent (write)" section for the full UI behaviour (individually confirmed, no bulk confirm, Cancel is local-only, cards are ephemeral). Holds `conversationId` in local state, set from every successful `askAgent` response; the conversation lives exactly as long as the modal stays open — closing it (✕) or tapping "New conversation" resets `conversationId` to null and clears both `messages` and any un-confirmed proposal cards (see FEATURES.md's "AI agent (memory)"). While `messages` is empty, renders THREE read-only starter suggestion chips — today / overdue / this week, deliberately no "Add a task" chip (see DECISIONS.md) — styled as the app's existing secondary pill buttons (e.g. `BrowseView.jsx`'s filter pills) that fill the input and send immediately when tapped; they disappear after the first message.
- `App.jsx` holds the Supabase session via `onAuthStateChange`; also captures the Google `provider_token`/`provider_refresh_token` after the calendar-connect OAuth flow (flagged via sessionStorage) and posts them to the backend.
- Today shows today's Google events inline; Calendar grid shows events as titled chips; a day-detail popup shows tasks + events; events are read-only in-app and tap-to-open in Google Calendar.
- `frontend/src/components/CollapsibleSection.jsx` — shared accordion-row shell (title button + rotating chevron + hidden/block content, never conditionally unmounted). Used by `SettingsModal.jsx` to make each of its seven sections independently collapsible, all closed by default.
