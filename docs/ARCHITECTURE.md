# ARCHITECTURE — stack, files, deployment, constants
_Single source of truth for the technical shape. Verify against real code when Claude Code bootstraps this; the code wins on any discrepancy._

## Stack
- **Backend**: FastAPI (Python) + Supabase (PostgreSQL) + Google Gemini. Fully migrated OFF Airtable (Airtable kept only as a read-only legacy backup).
- **Frontend**: React + Vite + Tailwind CSS + react-i18next (i18n: English + Greek, both fully translated) + @supabase/supabase-js.
  **CORRECTED**: an earlier draft said "Greek default + English". Verified against `frontend/src/i18n.js`: the default/fallback language is `en`; Greek (`el`) is a full, complete translation the user switches to manually via Settings → Language, and the choice persists in `localStorage` (`app_language`). There is no server-side or browser-locale-based Greek default.

## Backend files and responsibilities
- **main.py** — all FastAPI endpoints; `get_current_user_id` auth dependency (verifies the bearer token via `supabase.auth.get_user(token)`). Endpoint areas: tasks CRUD (`/tasks` GET/POST, `/tasks/{id}` PATCH/DELETE), extract (`/extract`, `/extract-voice`, `/extract-image`), agent (`/agent/query`, `/agent/confirm-action` — see FEATURES.md's "AI agent (write)" section), settings (`/settings` GET/PATCH), calendar (`/calendar/connect`, `/status`, `/disconnect`, `/test`, `/events`, `/events/{id}/convert`, `/events/{id}/dismiss`), profile/account (`/profile` GET/PATCH, `/account` DELETE), Hostaway webhook (`/webhooks/hostaway`), scheduler (`/notifications/run-scheduler`), dev (`/dev/token-usage`), `/health`. `/agent/confirm-action` re-validates every agent-proposed write from scratch server-side (type, field whitelist, enum/date/time values, user_id scoping) — it is the security boundary, never trusting the proposal the frontend echoes back.
- **repository.py** — ALL Supabase CRUD. Every function is scoped by `user_id` (except `get_all_tasks_for_scheduler`-style enumerations used by the per-user scheduler loop, which are intentionally global). App-code `user_id` filtering is the PRIMARY security boundary because the secret key bypasses RLS.
- **services.py** — TaskService; push sending (`send_push_to_user(user_id, ...)`); `run_notification_scheduler()` which loops every active user via `get_all_active_user_ids()`; Hostaway escalations; `sync_google_calendar_for_user(user_id)`. `create_task_manual(user_id, fields, approval_status=True)` — the `approval_status` param defaults `True` for the normal manual-create path (`POST /tasks`) and is passed `False` by `/agent/confirm-action` so an agent-created task lands in the Inbox for approval instead of the task list.
- **agent_engine.py** — Q&A + propose-then-confirm write AI agent. Manual tool-call loop against google-genai with Automatic Function Calling DISABLED (so token usage can be summed across every round — AFC undercounted). `ask_agent(question, user_id) -> {"answer": str, "proposed_actions": list[dict]}` loads that user's tasks into RAM, exposes the read tools (`search_tasks`, `get_task_details`) plus the write-proposal tools (`propose_complete_task`, `propose_update_task`, `propose_create_task`) from `agent_tools.build_write_proposal_tools`, and returns both the answer and whatever proposals were registered during the tool-calling loop. The propose_* tools never write to the database themselves — see FEATURES.md. The loop logs a `[agent][round N]` line per round (prompt/output/thinking/cached/total tokens plus which tools were called) and a `[agent][SUMMARY]` line per run covering every exit path including failures (`ok`/`no_answer`/`max_rounds`/`api_failure`/`max_rounds_recovered`) — this is log-only instrumentation for the ongoing token-cost investigation (see DECISIONS.md); `token_usage_log` writes via `token_tracker.log_token_usage()` are unchanged. `MAX_TOOL_ROUNDS` is now `4` (was `6`): hitting the ceiling no longer raises — one final tool-less `generate_content` call forces an answer from whatever was already found (system instruction unchanged, no `tools` passed so it cannot call anything), logged as `outcome=max_rounds_recovered`; only a genuinely empty final answer still raises.
- **agent_tools.py** — shared system instruction builder + read-tool factory (`search_tasks`, `get_task_details`) + write-proposal tool factory (`build_write_proposal_tools(proposed_actions, available_tasks)` → `propose_complete_task`/`propose_update_task`/`propose_create_task`) + `AGENT_WRITABLE_FIELDS` (the field whitelist `main.py`'s `/agent/confirm-action` re-checks against) + Greek→Latin transliteration for fuzzy keyword matching. `is_open_task(t, include_completed=False)` is the SINGLE SOURCE OF TRUTH for "counts as an open task" (not rejected, approved, not completed unless asked) — every open-task filter in the module (the main `search_tasks` loop, the `overdue_count` computation, the `no_matches_hint` lookup) routes through it, so the pending-approval policy only ever needs to change in one place. `PRIORITY_ORDER` ranks P1/P2/P3 for the chronological-then-priority sort. `build_time_context()` does the module's ONE clock read per request, returning `(today_iso, now_hhmm, header)` — `header` (a `[Now: ...]` / `[Next 7 days: ...]` block) is injected into the FIRST USER TURN by `agent_engine.ask_agent`, not into the system instruction; `build_system_instruction(today_iso, now_hhmm)` and `build_tool_functions(cached_tasks, today_iso)` both take their date/time from the same resolved values instead of reading the clock themselves. Holds the CONFIDENTIALITY, DATA-VS-INSTRUCTIONS, TIME AWARENESS, DATE RESOLUTION, OVERDUE TASKS, NO MATCHES, and WRITE ACTIONS directives (the last one tells the agent to always present a proposal as pending, never as already executed).
- **ai_engine.py** — Gemini extraction from text/voice/image into structured task data.
- **hostaway_integration.py** — Hostaway webhook AI classification, OAuth callback, enrichment, and `get_user_id_for_hostaway_account()` (the "one door": currently hardcoded to the owner user_id; the ONLY function to change when multiple users connect their own Hostaway later).
- **google_calendar.py** — per-user Google token management (`get_valid_access_token`), `sync_task_to_google_calendar`, `pull_calendar_changes`, `test_calendar_connection`, `delete_calendar_event`, `mark_event_completed`.
  **CORRECTED**: an earlier draft described `get_valid_access_token` as doing a "proactive 5-min-buffer refresh via `_refresh_access_token`". Verified against the actual code: there is no separate `_refresh_access_token` helper, and the refresh is REACTIVE, not proactive — it only refreshes when `datetime.now(timezone.utc) >= expiry` (i.e. after the token has already expired), with no buffer margin. Same correction applies to DECISIONS.md and PROJECT_STATUS.md.
- **token_tracker.py** — per-user, per-model cost logging (`log_token_usage(..., user_id)`, `get_usage_summary(user_id)`).
- **migrate_to_supabase.py** — one-off Airtable→Supabase migration script (reads raw Airtable REST API). Historical; kept for reference.

## Frontend shape
- Views: Inbox / Today / Upcoming / Calendar (Monthly + Weekly) / Browse, plus the agent chat and Settings modal.
- `api.js` wraps all backend calls with an authenticated fetch (bearer token from the Supabase session). `askAgent(question)` returns the full `{answer, proposed_actions}` object (not just the answer string); `confirmAgentAction(action)` posts one proposed action to `/agent/confirm-action` and returns `{status, message, task}`.
- `AgentChatModal.jsx` renders one confirmation card per proposed action directly under the assistant reply it came from — see FEATURES.md's "AI agent (write)" section for the full UI behaviour (individually confirmed, no bulk confirm, Cancel is local-only, cards are ephemeral).
- `App.jsx` holds the Supabase session via `onAuthStateChange`; also captures the Google `provider_token`/`provider_refresh_token` after the calendar-connect OAuth flow (flagged via sessionStorage) and posts them to the backend.
- Today shows today's Google events inline; Calendar grid shows events as titled chips; a day-detail popup shows tasks + events; events are read-only in-app and tap-to-open in Google Calendar.
- `frontend/src/components/CollapsibleSection.jsx` — shared accordion-row shell (title button + rotating chevron + hidden/block content, never conditionally unmounted). Used by `SettingsModal.jsx` to make each of its seven sections independently collapsible, all closed by default.
