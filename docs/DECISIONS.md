# DECISIONS — choices + rationale (current decisions only)
_Append-only in spirit, but SUPERSEDED decisions move to DECISIONS_ARCHIVE.md (kept in git, excluded from the Project index) so retrieval can never mistake a cancelled decision for a current one. When a spec overturns a decision, name what's superseded and have the new entry reference what it replaced. Criterion for staying here: "does this still govern the code?"_

### Decision: Supabase over Airtable — for real multi-user + RLS
Migrated fully to Supabase (PostgreSQL) to get per-user rows, RLS, indexes, foreign keys, and real auth. Supersedes the original Airtable backend (that decision is archived). Airtable kept read-only as a legacy backup.

### Decision: secret key bypasses RLS → app-code filtering is the PRIMARY defense
The backend talks to Supabase with the secret key, which intentionally bypasses RLS (needed for cross-user work like the scheduler). Therefore every repository function must filter by `user_id` in application code; RLS is defense-in-depth, not the primary guard. Never rely on RLS alone in backend code. Seeing other users' rows in the Supabase Table Editor (an admin tool) is normal and NOT a leak.

### Decision: dates stored as TEXT
Kept due_date/due_time as TEXT during migration to avoid rewriting all date logic. Accepted trade-off.

### Decision: agent runs a manual tool-call loop with AFC disabled
google-genai's Automatic Function Calling under-reported token usage (only the last round). Running the loop manually lets us sum usage across every round accurately. Plain Python functions are still passed as tools (SDK still auto-generates their schemas).

### Decision: agent is stateless per question; only filtered results reach the LLM
Each question re-loads that user's tasks into RAM, filters in Python (free), and passes only the small filtered result to the LLM. Keeps cost bounded regardless of task count.
**Refined by** "agent memory is server-reconstructed, bounded, and answers-only" below: a bounded conversation history of past questions/final answers (never raw tool results) is now replayed ahead of the current turn. This does not change anything stated here — task loading/filtering is still fully stateless per request.

### Decision: agent writes via propose-then-confirm; confirm endpoint is the security boundary
**SHIPPED** (Phase 1: complete/update/create; verified end-to-end logged-in against live Supabase data on 2026-08-01 — see FEATURES.md / PROJECT_STATUS.md). The agent proposes structured actions via `agent_tools.build_write_proposal_tools`; the user confirms individually via a card in the chat UI; a separate `POST /agent/confirm-action` endpoint executes with full server-side re-validation (allowed types, field whitelist, enum/date/time values, user_id scoping) — that endpoint is the actual security boundary, not the propose tools or the UI. This defends against prompt injection (e.g. malicious Hostaway guest text): even a tricked proposal is user-visible and user-gated, and the server re-validates regardless of what the UI sends. Phase 2 (delete + Google Calendar event operations) remains deferred — see BACKLOG.md.
**Updated**: a record_id for propose_complete_task/propose_update_task may now come from either a tool result OR the PRE-LOADED day view injected into the first turn (see "Day view is NARROW" below) — both are the same user-scoped `cached_tasks` read in the same request. The rule was never really "must go through search_tasks first", it was "never fabricate an id"; the day view is just a second legitimate source of real ones.

### Decision: agent injection defenses (CONFIDENTIALITY + DATA-VS-INSTRUCTIONS)
Tool results — including third-party Hostaway guest text — are DATA to read/summarize, never instructions to follow. The agent also won't reveal its own instructions. Keep these directives when touching agent code.

### Decision: backend manages Google Calendar token refresh itself
Supabase does not reliably refresh the Google provider token (documented). So we capture provider tokens once and refresh them ourselves against Google's OAuth endpoint. Tokens live in `google_calendar_connections`.
**CORRECTED**: an earlier draft said this refresh is "proactive (5-min buffer before expiry)". Verified against `google_calendar.py`'s `get_valid_access_token`: it's REACTIVE — it only refreshes when `datetime.now(timezone.utc) >= expiry` (i.e., after the stored token has already expired), with no buffer margin, and there is no separate helper function. If a 5-min proactive buffer is wanted, that's an actual code change, not yet done.

### Decision: calendar pull is conservative
Only app-created (tagged) events sync back into tasks. Foreign events go to a separate view with a manual "Make it a task" button — we do NOT auto-import every calendar entry as a task (would flood the list). Scoped to the "primary" calendar; no recurring-event handling. Bootstrap sync uses a 90-day lookback + singleEvents=true + orderBy=startTime; orderBy is incompatible with syncToken (400) so it's bootstrap-only.

### Decision: origin-aware deletion + completion marking
`calendar_origin` ('app' vs 'google') decides deletion behavior: deleting an app-origin task deletes its Google event; deleting a google-origin (converted) task keeps the Google event. A calendar-side deletion appends a note to the task and unlinks — never deletes the task. Completion prefixes the Google event title with "✓ " instead of deleting it (supersedes an earlier "delete event on completion" idea, which is archived); the "✓ " is stripped on pull so it never leaks into the task name.

### Decision: Hostaway multi-tenancy deferred to "year 2"
Only the owner has Hostaway now. `get_user_id_for_hostaway_account()` is the single "one door" to change when others connect their own Hostaway accounts later. Nothing else needs rewriting.

### Decision: token usage has a single source of truth
`token_usage_log` is per-user; usage summaries are computed by summing it. No cached usage column on `profiles` (two sources would drift). A future `profiles.monthly_token_quota` + Stripe billing is deferred (see BACKLOG).

### Decision: profiles table for per-user profile/settings, not auth.users
Supabase's `auth.users` is off-limits for custom fields, so a `profiles` table (1:1, auto-created on signup) holds display_name/email and is the right home for future per-user settings.

### Decision: Settings sections collapse independently, closed by default, hidden-not-unmounted
Each of Settings' seven sections (My Profile, Notifications, Google Calendar, Language, Developer, Account, About) is now a collapsible accordion row (`CollapsibleSection`), all closed the moment the modal opens. Rationale: the long single-scroll modal was unusable on mobile once My Profile + Settings redesign added more sections. Independent toggles (not one-open-at-a-time) were chosen over a strict accordion so the user can compare two sections at once (e.g. Notifications and Calendar) without losing either's state. Collapsed content is hidden via a CSS class, not unmounted — this preserves in-progress form state (e.g. a partially typed display_name) across a collapse/expand and avoids re-running a section's own data-fetching effects every time it's re-opened. This supersedes NOTHING — FEATURES.md's "single scrollable modal, not sub-page navigation" characterization of Settings still stands; this only changes each section from always-expanded to collapsible within that same single modal.

### Decision: docs/knowledge workflow (this restructure)
State lives in /docs (single source of truth), not in long chats. One task = one chat (cost grows quadratically within a chat). The Project indexes ONLY /docs, never code. Retrieval is semantic search over chunks; cold-start uses rare anchor strings. Facts are never hardcoded in the system instruction (they drift); the only deliberate exception is the hosting/workflow SHAPE.

### Decision: measure the agent's token cost before optimizing it
An optimization proposal (implicit caching, a pre-loaded day view, compact tool results, merging the propose_* tools) was reviewed and NOT adopted as written, because every figure in it was inferred rather than observed. A read-only query over existing token_usage_log rows then established, before any code was written: thinking tokens are zero (so a thinking-budget change is off the table entirely); input is ~90% of tokens and ~77% of cost; the fixed per-round prefix is ~1,830 tokens; the average call is ~4,264 tokens, and the "16k" figure that prompted this work is the tail, not the typical case. Cost scales with the NUMBER OF TOOL ROUNDS.
Two constraints on any future work, from the same review: (a) the tool result is appended to `contents` and therefore re-sent on every subsequent round, so compacting it saves proportionally more the more rounds a question takes; (b) implicit caching and round-reduction are substitutes, not complements — removing a round also removes the cache hit that round would have produced, and at a ~1,830-token prefix the app sits near the minimum input threshold implicit caching requires, so caching may never engage at all. Supersedes nothing.

### Decision: agent instrumentation is log-only; token_usage_log writes are unchanged
Per-round and per-run token figures (including thinking and cached counts) go to the application log only. They are deliberately NOT passed to `token_tracker.log_token_usage()`. Rationale: a write to `token_usage_log` containing a field with no matching column is rejected wholesale and silently breaks ALL token logging (documented in DATABASE_SCHEMA.md) — and this change exists precisely to make measurement reliable. Persisting thinking/cached counts is a separate task requiring a migration first.

### Decision: agent search results sort chronologically, not priority-first
`search_tasks` sorts by (due_date, due_time, priority) before capping. The cap's purpose is "the next N things to do", and a P1 due next week is not more urgent than a P3 due today. Consequence: a high-priority far-future task can fall outside the cap; the `truncated` flag tells the agent to mention that more matches exist.
Supersedes nothing (there was previously no sort at all — an arbitrary subset was kept).

### Decision: one open-task predicate, changeable in exactly one place
`agent_tools.is_open_task(t, include_completed=False)` is now the only place "counts as an open task" (not rejected, approved, and not completed unless asked) is decided — the `search_tasks` main filter, the `overdue_count` computation, and the `no_matches_hint` lookup all route through it instead of each carrying its own inline copy of the same three-condition check. Rationale: the pending-approval policy is a product decision that is still open (see CURRENT_TASK.md) — when it changes, it must change in one function, not require re-auditing every place the three fields were checked inline. Supersedes nothing (there was previously no single predicate, just duplicated inline checks).

### Decision: the round ceiling degrades gracefully instead of raising
Previously, exhausting `MAX_TOOL_ROUNDS` raised a `RuntimeError` that surfaced to the user as a failure — meaning the single most expensive run (every round used) was also the one guaranteed to look broken. It now makes one additional tool-less call, explicitly told to answer NOW from whatever was already found, and returns that answer instead of an exception; only a still-empty final answer raises. This is logged as `outcome=max_rounds_recovered`, deliberately distinct from `outcome=ok` — the run still signals that something went wrong (too many rounds needed), the user just no longer pays for it with a 500. A partial, honest answer beats an exception. Paired with lowering `MAX_TOOL_ROUNDS` from 6 to 4: without this decision that change would only have surfaced the error more often; with it, the worst case gets cheaper and still answers.

### Decision: calendar arithmetic is resolved in Python, never computed by the model
Weekday names ("Τετάρτη", "Monday") and the "overdue" date bound are both calendar arithmetic — exactly the kind of thing a language model does unreliably. Rather than asking the model to compute "next Wednesday" or "yesterday" from a stated today-date, the actual dates are resolved once per request in Python (`agent_tools.build_time_context`) and handed to the model as a `[Next 7 days]` lookup table in the user turn; the model's job is to READ the answer, not calculate it. Supersedes nothing — this generalizes the existing single-clock-read design (previously only `today_iso` for the today/overdue checks) to also cover weekday resolution.

### Decision: implicit caching is NOT available — the only cost lever is a smaller prefix
**Measured, not assumed** (2026-08-02, `gemini-3.1-flash-lite-preview`): three byte-identical back-to-back `ask_agent()` calls all reported `cached=0`, and a raw `generate_content` response contains **no cache field at all** in `usage_metadata` (`cached_content_token_count` is absent, not zero). Implicit caching does not engage for this model at this prefix size, full stop.
Consequence: an earlier proposal to make `build_system_instruction()` static (removing the per-minute `now_hhmm` interpolation, which does make the prefix change every 60s) was **dropped** — it was justified entirely by unlocking caching, and there is no caching to unlock. It buys ~30 tokens of de-duplication for a reword of TIME AWARENESS that cannot currently be verified against real data (the owner account has no timed tasks due today). Revisit only if Google enables caching for this model.
Therefore the ONLY lever on per-round cost is **making the prefix itself smaller**. Measured breakdown per round, before the compression below: system instruction 2.473 tokens (60%), read tools 477, propose tools 762 (18%), day view + header + question ~400. Total fixed prefix 3.712 tokens, paid raw on every single round.

### Decision: the system instruction is compressed and de-duplicated, not appended to
The instruction had grown to 10.532 characters / 2.473 tokens across 14 sections, because every behavioural bug was fixed by appending prose — and that prose is taxed on every round of every request forever. Rewritten to 6.092 characters / **1.490 tokens (-40%)**, cutting the fixed prefix from 3.712 to **2.729 (-26%)** and measured end-to-end at **-23% total tokens on every acceptance test**, with zero behavioural regression (identical round counts and correct answers across all 9 read tests).
What was merged: `SEARCH SCOPE` + `CATEGORY MATCHING` + `FILTER DISCIPLINE` + `KEYWORD SEARCHES ARE FUZZY` → one `FILTERS` section; `UNDATED TASKS` + `RESULT LIMITS` + `NO MATCHES` → one `RESULTS` section. This was not only compression — `CATEGORY MATCHING` ("Do not leave category empty out of caution") directly contradicted `SEARCH SCOPE` ("Otherwise leave it empty"), and the contradiction was live in production (see below). Rule of thumb going forward: a new behavioural rule belongs INSIDE an existing section, and if it contradicts one, the old one is what's wrong.

### Decision: a name lookup passes keyword only, and retries with include_completed
Two production bugs found by running the acceptance list directly against `ask_agent()` (2026-08-02):
1. **Invented filters survived on the write path.** "σημείωσε το <task> ως ολοκληρωμένο" produced `search_tasks(date_from=today, date_to=today, category=Personal, keyword=...)` — neither the date nor the category came from the user. The `SEARCH SCOPE` rule was working for read questions but being overridden here, most likely by `CATEGORY MATCHING`'s "do not leave category empty" plus `DATE RESOLUTION`'s single-day rule bleeding into a request with no date at all. Fixed by the merge above plus an explicit rule: *looking up a task the user NAMED in order to act on it is a name lookup — pass keyword ONLY, never a date or category you inferred rather than heard.*
2. **`include_completed` was never used.** Nothing told the agent to retry with it, so an already-completed task was reported as "I couldn't find that task" — a wrong answer, produced at the most expensive path in the whole suite (3 rounds, 13.017 tokens). Fixed by an explicit rule to retry ONCE with `include_completed=true` before concluding a named task does not exist. Now 2 rounds, 6.545 tokens, and the correct answer ("it is already completed") — **-50% and correct**.
Both are the same underlying failure mode the project has now hit three times: two instructions that disagree, with the model picking whichever it likes. Supersedes nothing; tightens "the agent never invents search filters".

### Decision: the agent never invents search filters it was not given
Production logs showed the model adding category and priority filters to a question that contained neither, and inventing a 7-day window for a question with no time reference. Both returned plausible answers over silently narrowed data. Filters are therefore constrained explicitly in the system instruction, and an over-broad search is preferred to a narrowed one. Related: the [Next 7 days] map is a lookup table, never a search range. Supersedes nothing.

### Decision: the pre-loaded day view is NARROW — today + overdue only, not a week
Measured baseline: every agent question costs exactly 2 rounds (1 search + 1 answer) at ~3,350 tokens/round, and the round count is the entire cost driver. Pre-loading today's and overdue open tasks into the first turn removes that lookup round for day-scoped questions (~7,000 → ~3,600 tokens for reads, ~10,700 → ~7,100 for writes on today's tasks). A 7-day horizon was considered and rejected: measured cost is ~130–165 tokens per task, so a week-wide injection would cost ~2,000–2,500 tokens on EVERY single request to save ~3,350 on only the minority that actually ask about the coming week — the wrong trade in the opposite direction from what this whole effort is trying to achieve. Supersedes "today-scoped searches report an overdue COUNT, not the overdue tasks" (moved to DECISIONS_ARCHIVE.md) — the day view lists the actual (capped) overdue tasks at no extra round, making a count-only mechanism pointless; having both would also mean two mechanisms answering the same question, which is exactly the shape of bug the previous PR (invented search filters) had to fix.

### Decision: day-view overdue/pending sections are capped with an explicit overflow line
Overdue tasks accumulate without bound in a real to-do app (nothing removes them from "overdue" except completing or rescheduling them), so an uncapped section would improve the AVERAGE per-request cost while making the WORST case unbounded — the opposite of this PR's goal. `DAY_VIEW_OVERDUE_CAP` (10) and `DAY_VIEW_PENDING_CAP` (5) bound both sections; a "(+N more ...)" line tells the agent (and, via its answer, the user) that more exist rather than silently truncating. `TODAY` is deliberately NOT capped — a single day's tasks are bounded by nature. Supersedes nothing.

### Decision: tasks pending approval get their own day-view section instead of being made "open"
Tasks awaiting Inbox approval (mostly AI-extracted or Hostaway webhook tasks) are NOT "open" — `is_open_task()` correctly excludes them, and that meaning is unchanged. But a Hostaway task escalating today while completely invisible to "what do I have today?" is the worst failure mode for the actual business this app supports (a real Airbnb/short-let operation where those escalations matter). `is_pending_task(t)` is the single source of truth for this separate policy — not rejected, not completed, `approval_status` false — and the day view surfaces pending tasks due today or already late in their own PENDING APPROVAL section, explicitly NOT merged into OVERDUE/TODAY, with the system instruction telling the agent to describe them as awaiting approval and never propose a write on one. Supersedes nothing — this is a new, additive surface, not a change to what "open" means.

### Decision: agent memory is server-reconstructed, bounded, and answers-only
Replaying raw tool results would multiply the cost the day view was built to reduce: a tool result is appended to `contents` and therefore re-sent on every subsequent round WITHIN a request (see "implicit caching is NOT available" above), so replaying it across turns TOO would compound that same cost again. Questions and final answers are small and do not compound the same way. The client sends only a `conversation_id`, never the messages themselves, because a client that sends its own history controls both the prompt shape and the bill; the backend enforces `HISTORY_MAX_PAIRS` (4 pairs / 8 messages), `HISTORY_MSG_MAX_CHARS` (500) and `HISTORY_MAX_REFS` (5) regardless of what a client would send. Same shape as `/agent/confirm-action` being the actual write boundary rather than trusting the client's echoed proposal.
This IMPLEMENTS the BACKLOG item "Agent multi-turn memory". It REFINES (does not supersede) "agent is stateless per question; only filtered results reach the LLM" above — the agent is still stateless with respect to tool results, and still re-loads and re-filters all of that user's task data fresh on every single request; only the visible conversation TEXT (questions + final answers) now persists and is replayed, bounded and server-enforced.

### Decision: history resolves references only, never supplies task facts
History may be stale by minutes or hours — nothing re-verifies an earlier answer before replaying it. Task facts therefore always come from the fresh day view or a fresh tool call in the CURRENT turn, never from what an earlier answer said; history exists solely to resolve references ("it", "that one", "change it to Friday"). A `[refs: name=id]` line in an earlier answer is a legitimate record_id source — it came from a real tool result earlier in the same conversation — but it is not exempt from validation: it still has to match a task in the current, freshly-loaded, user-scoped task list before `propose_update_task`/`propose_complete_task` will act on it, and is re-validated again server-side by `/agent/confirm-action`. A deleted or since-changed task simply fails that validation and the agent falls back to `search_tasks`. Ambiguous follow-ups (e.g. "set it to 5" — day of month or hour?) are clarified with a question, never guessed, because a guessed value would appear on a confirmation card the user may accept without reading closely. Supersedes nothing.

### Decision: one table (agent_runs) is both the debug archive and the memory source
Agent behaviour is verified by asking real questions and checking whether the model called the right tools — but Render's application logs are ephemeral, so a verification pass run against them leaves nothing behind and has to be redone from scratch. Persisting each run — including the exact first-turn text the model saw and every round's tool calls — turns verification into a SQL query and makes a wrong answer diagnosable after the fact: you can see what the model had in front of it, not just what it replied. Full text is stored because it costs ZERO tokens (nothing in this table is ever sent to the model) and a few KB of storage.
A separate `agent_messages` table was created and then dropped before use: one row of `agent_runs` already IS a question/answer pair, so a second table would have stored the same text twice and created a second source of truth. `repository.get_recent_agent_runs` now reads the same table `log_agent_run` writes — the debug archive and the bounded conversation memory (see "agent memory is server-reconstructed, bounded, and answers-only" above) are the same write and the same rows, not two parallel systems that could drift.
Constraint: this table is diagnostic + memory only and is never summed for usage or billing; that remains `token_usage_log`, per "token usage has a single source of truth". The insert builds its column list explicitly rather than splatting a dict, per the documented failure where one unknown field silently broke all token logging.
Also: the agent chat's starter chips are read-only questions only — no "Add a task" chip, because creating a task via the agent costs a proposal round for what the add-task form does for free. Supersedes nothing.

### Decision: a rule the code can enforce does not belong in the system instruction
Five behaviours were failing in live testing (3 of 10 questions, 2026-08-06), and every one of them had already been "fixed" once by appending prose to the system instruction. That is why they came back: the instruction had grown to 7.4k characters, is paid on every round of every request, and the model demonstrably drops individual lines from it. The clinching evidence: `"τι πρέπει να ψωνίσω;"` appears in the instruction VERBATIM as a worked example showing exactly which filters not to pass, and the model still passed all three of them.
The rule going forward: if code can enforce it, code enforces it, and the prose comes OUT. Applied to — the pending-approval write ban (now refused in `propose_complete_task`, `propose_update_task` and `/agent/confirm-action`; previously it existed ONLY as one instruction line, so an approval bypass was one dropped line away and nothing in the codebase would have stopped it); the `include_completed` retry (now done inside `search_tasks`, was costing a full round every time a named task was already completed); the enumerated `propose_update_task` field list (duplicated the SDK-generated schema, which the model cannot violate anyway); the duplicated record_id rule (already enforced by `_find_task`).
Supersedes nothing, but it REVERSES the working assumption behind "the system instruction is compressed and de-duplicated, not appended to" — that decision said a new rule belongs INSIDE an existing section. This one says the first question is whether it belongs in the instruction at all.

### Decision: a tool result carries its own instructions, next to the data
`truncated: true` was observed being silently dropped: the rule telling the model to report it lived ~40 lines away in the system instruction, disconnected from the moment the model actually reads the number. The fix that worked — already proven by the pre-existing `no_matches_hint` — is to attach a short, numbers-filled instruction to the result itself, computed from that call's own data.
Now standard for every result-shaped signal: `truncated_hint`, `undated_hint`, `fuzzy_keyword_note`, `completed_only_note`, `over_filtered_hint`. A hint that RETURNS THE ROWS beats one that describes them: measured in the same test run, the fallbacks that hand back data (`completed_only_note`, `fuzzy_keyword_note`) resolve in 2 rounds, while `over_filtered_hint` in its describe-only form cost 3-4 because the model had to run a second search to fetch what the first call already held. `over_filtered_hint` therefore also returns `relaxed_matches`.
Constraint: hints are additive fields on the result, never a replacement for the honest `tasks`/`total_matches` of the query as asked. An over-filtered search still reports 0 matches for the filters it was given; the relaxed rows arrive alongside, labelled.

### Decision: filter examples show the WHOLE call, with nulls written out
The FILTERS section listed only the arguments to pass, with a negative aside ("NOT Personal, NOT P3, NOT today"). That is the formulation the model ignored on a verbatim-matching question. Rewritten so every example spells out EVERY parameter including the ones that stay empty (`keyword="ψώνια" category=null priority=null date_from=null date_to=null undated_only=false`), turning "not mentioned" into a value the model must actively produce rather than a field it can quietly fill in — positive instruction instead of negative.
Measured before/after on the same live questions: invented filters dropped from 6 occurrences to 1 across 29 questions, and the five questions that had been costing an extra round each stopped doing so (-11% total tokens across the suite, -70% on the worst single case). Verified separately that this did NOT over-correct into writing null everywhere: a 15-question category/priority matrix (including the synonyms "δουλειές" → Business, "μηνύματα από επισκέπτες" → Hostaway, "σημαντικά" → P1, and repeats for stability) set the right filter 14/14 times, with the one nominal failure being a question correctly answered from the day view with no search at all.
This is the counter-example to the decision above: prose CAN work, but only when it states the required output shape rather than forbidding a wrong one. Supersedes the example format introduced with the FILTERS/DATE RESOLUTION merge.

### Decision: Greek inflection is handled by prefix stemming, not a real stemmer
A task named "Ραντεβού οδοντιάτρου" was invisible to a search for "οδοντίατρος": the match is a literal substring and Greek inflects the ending. No instruction and no larger model can fix a tool that never returns the row. Greek changes word endings and never word starts, so `stem_words()` compares a 5-character accent-folded prefix per word (words under 6 chars are dropped rather than stemmed — a 5-char prefix of a short common word matches nearly everything).
It joins the existing exact → word-level fallback chain as a third tier, so it is only consulted when the exact pass returned nothing, which contains the over-matching this deliberately loose comparison would otherwise cause.
Explicitly NOT the right long-term answer: Supabase is already PostgreSQL, whose bundled Snowball dictionaries include Greek, so `to_tsvector('greek', ...)` is the correct fix and would also fix stemming inside descriptions properly. This buys the common case with no schema change and no per-query round trip. Revisit when the logs show word-level matching firing often.

### Decision: the filters the agent searched with are shown to the user
Every other guard against invented filters is the agent policing itself. The agent was observed answering "you have none" over a search it had narrowed with a category and a date the user never mentioned — and the narrowing was completely invisible. `/agent/query` therefore returns the filters of each `search_tasks` call it made, and the chat renders them under the answer ("Έψαξα: σε Business, από 2026-08-06 έως 2026-08-13 · 1 βρέθηκαν").
This does not prevent an invented filter; it makes one impossible to miss, because only the user knows what they actually meant. Same principle as the confirmation cards: show the machine's intent before it matters instead of asking to be trusted. This is also how production tools solve it — Todoist's Filter Assist has the LLM emit a filter query that the user then SEES and can edit, rather than searching on the user's behalf invisibly.
Only filters actually passed are listed; rendering an omitted filter as a constraint would be its own lie.

### Decision: a scope the tools cannot express is a missing parameter, not a prompting problem
"Τι έχω χωρίς προθεσμία;" had no expressible form — `search_tasks` could filter BY a date range but not FOR the absence of one. The model compensated by searching category by category looking for undated rows: 5 rounds and 27.919 tokens for a one-line answer, the single most expensive observed run in the suite. Adding `undated_only` made the same question 2 rounds and 8.271 tokens (-70%).
Generalises: when the model takes an obviously roundabout path, check first whether the direct path exists in the tool surface at all. `undated_only` overrides `date_from`/`date_to` rather than combining with them, since "no date" and "a date range" are contradictory and silently returning nothing would be the worst reading of the two.
