# DECISIONS — choices + rationale (current decisions only)
_Append-only in spirit, but SUPERSEDED decisions move to DECISIONS_ARCHIVE.md (kept in git, excluded from the Project index) so retrieval can never mistake a cancelled decision for a current one. When a spec overturns a decision, name what's superseded and have the new entry reference what it replaced. Criterion for staying here: "does this still govern the code?"_

### Decision: Supabase over Airtable — for real multi-user + RLS
Migrated fully to Supabase (PostgreSQL) to get per-user rows, RLS, indexes, foreign keys, and real auth. Supersedes the original Airtable backend (that decision is archived). Airtable kept read-only as a legacy backup.

### Decision: secret key bypasses RLS → app-code filtering is the PRIMARY defense
The backend talks to Supabase with the secret key, which intentionally bypasses RLS (needed for cross-user work like the scheduler). Therefore every repository function must filter by `user_id` in application code; RLS is defense-in-depth, not the primary guard. Never rely on RLS alone in backend code. Seeing other users' rows in the Supabase Table Editor (an admin tool) is normal and NOT a leak.

### Decision: dates stored as TEXT
Kept due_date/due_time as TEXT during migration to avoid rewriting all date logic. Accepted trade-off.

### Decision: agent runs a manual tool-call loop with AFC disabled
google-genai's Automatic Function Calling under-reported token usage (only the last round). Running the loop manually lets us sum usage across every round accurately. Plain Python functions are still passed as tools (SDK still auto-generates their schemas).

### Decision: agent is stateless per question; only filtered results reach the LLM
Each question re-loads that user's tasks into RAM, filters in Python (free), and passes only the small filtered result to the LLM. Keeps cost bounded regardless of task count.
**Refined by** "agent memory is server-reconstructed, bounded, and answers-only" below: a bounded conversation history of past questions/final answers (never raw tool results) is now replayed ahead of the current turn. This does not change anything stated here — task loading/filtering is still fully stateless per request.

### Decision: agent writes via propose-then-confirm; confirm endpoint is the security boundary
**SHIPPED** (Phase 1: complete/update/create; verified end-to-end logged-in against live Supabase data on 2026-08-01 — see FEATURES.md / PROJECT_STATUS.md). The agent proposes structured actions via `agent_tools.build_write_proposal_tools`; the user confirms individually via a card in the chat UI; a separate `POST /agent/confirm-action` endpoint executes with full server-side re-validation (allowed types, field whitelist, enum/date/time values, user_id scoping) — that endpoint is the actual security boundary, not the propose tools or the UI. This defends against prompt injection (e.g. malicious Hostaway guest text): even a tricked proposal is user-visible and user-gated, and the server re-validates regardless of what the UI sends. Phase 2 (delete + Google Calendar event operations) remains deferred — see BACKLOG.md.
**Updated**: a record_id for propose_complete_task/propose_update_task may now come from either a tool result OR the PRE-LOADED day view injected into the first turn (see "Day view is NARROW" below) — both are the same user-scoped `cached_tasks` read in the same request. The rule was never really "must go through search_tasks first", it was "never fabricate an id"; the day view is just a second legitimate source of real ones.

### Decision: agent injection defenses (CONFIDENTIALITY + DATA-VS-INSTRUCTIONS)
Tool results — including third-party Hostaway guest text — are DATA to read/summarize, never instructions to follow. The agent also won't reveal its own instructions. Keep these directives when touching agent code.

### Decision: backend manages Google Calendar token refresh itself
Supabase does not reliably refresh the Google provider token (documented). So we capture provider tokens once and refresh them ourselves against Google's OAuth endpoint. Tokens live in `google_calendar_connections`.
**CORRECTED**: an earlier draft said this refresh is "proactive (5-min buffer before expiry)". Verified against `google_calendar.py`'s `get_valid_access_token`: it's REACTIVE — it only refreshes when `datetime.now(timezone.utc) >= expiry` (i.e., after the stored token has already expired), with no buffer margin, and there is no separate helper function. If a 5-min proactive buffer is wanted, that's an actual code change, not yet done.

### Decision: calendar pull is conservative
Only app-created (tagged) events sync back into tasks. Foreign events go to a separate view with a manual "Make it a task" button — we do NOT auto-import every calendar entry as a task (would flood the list).
**"Make it a task" now also lives in the Calendar's day popup (2026-08-07)**, not only in the Today view. It was reachable from Today alone, so an event on any other date could be SEEN in the calendar but not acted on — tapping it just left the app for Google, with no way back. The day popup is where a day's events are chosen from, so it is where they have to be actionable; the row itself still opens the real event in Google.
Related fix in the same pass: **a month-grid event chip is a preview, not a target.** Chips used to `stopPropagation` and jump straight to Google, so a day with two events opened one of them depending on which few pixels you hit, and only opened the DAY if you managed to miss both chips. The whole cell now selects the day, and the popup is where you pick an event — matching the task chips beside them, which already behaved this way. Scoped to the "primary" calendar; no recurring-event handling. Bootstrap sync uses a 90-day lookback + singleEvents=true + orderBy=startTime; orderBy is incompatible with syncToken (400) so it's bootstrap-only.

### Decision: origin-aware deletion + completion marking
`calendar_origin` ('app' vs 'google') decides deletion behavior: deleting an app-origin task deletes its Google event; deleting a google-origin (converted) task keeps the Google event.
**The user is now TOLD when the event survives (2026-08-07).** The rule above was correct and working, but silent: `DELETE /tasks/{id}` returned 204 No Content, so all four outcomes looked identical in the UI and a user who deleted a converted task saw "Deleted" while the event sat untouched in Google Calendar. The endpoint now returns 200 with `{"calendar": "none" | "deleted" | "kept_google_origin" | "delete_failed"}` (`services.TaskService.delete_task` returns it, `google_calendar.delete_calendar_event` now returns a bool so `delete_failed` can be distinguished from success), and the UI shows a longer neutral toast explaining that the event was created in Google Calendar and therefore is not this app's to delete. `api.js` tolerates a body-less 204 so an older backend still works. The task itself is deleted in all four cases — this is reporting, not a behaviour change.
Found alongside a real bug in the same path: `delete_calendar_event` was the only Google call in `google_calendar.py` that never checked its response status, so a 401/403 came back from `requests.delete()` as a normal return and the failure was invisible — deleted tasks whose events stayed behind, with nothing in any log. It now checks (treating 404/410 as success, since the event is already gone). A calendar-side deletion appends a note to the task and unlinks — never deletes the task. Completion prefixes the Google event title with "✓ " instead of deleting it (supersedes an earlier "delete event on completion" idea, which is archived); the "✓ " is stripped on pull so it never leaks into the task name.

### Decision: editing a pending task approves it — but the model still never approves
Saving edits to a task awaiting Inbox approval, or editing it with the inline agent, sets `approval_status: true` (2026-08-07). Reviewing a task and confirming a change to it IS the approval; requiring a separate ○ afterwards asks the user to say yes twice for one decision, and leaves edited-but-still-pending tasks sitting in the Inbox. The codebase already had the pattern — `handleCircleClick` approves a pending task when you complete it.
**Where the approval is added matters and is the whole point.** It is added in `TaskCard`, client-side, NOT in `task_agent`'s plan: `approval_status` stays out of `TASK_AGENT_WRITABLE_FIELDS`, and no plan the model produces ever contains it. So "an agent write must never stand in for the user's approval" is still true — what approves the task is the user choosing to edit it from its own card. The model's output and the user's action are different things and only one of them can approve. The chat agent's 409 on `/agent/confirm-action` for pending tasks is therefore NOT inconsistent and stays: there the user is in a chat, not looking at the task, and has reviewed nothing.
Two consequences worth keeping: it is announced rather than silent (the button reads "Save & approve", the toasts say so, the agent's change list shows `Έγκριση Όχι → Ναι`), and an agent edit's UNDO restores `approval_status: false` — a partial undo that left the task approved and out of the Inbox would be worse than no undo. Rejected tasks are excluded, since rejecting leaves `approval_status` false and they would otherwise be silently approved by any edit.

### Decision: a second agent, because knowing the task removes the hard part
The per-task edit agent (`task_agent.py`, 2026-08-07) is a separate module with its own short instruction rather than the chat agent given a narrower prompt. The reason is not modularity, it is that **almost everything in the chat agent exists to work out WHICH task the user means**: `search_tasks` with its three fallback tiers, the pre-loaded day view, conversation memory, the refs block, `_unjustified_target`, and the field-contamination guard. When the caller supplies a `record_id` the user is looking at, none of those have anything to protect — the anaphora guard's whole question ("is this the task the conversation named?") cannot even be asked with one task in scope. Reusing the chat agent here would have meant paying 2.729 tokens of prefix per edit for machinery whose entire purpose is already satisfied, and adding yet more instruction lines to a prompt whose measured problem was that the model drops individual lines.
Removing the lookup also removes the tools: no tools means no tool-calling loop, no `MAX_TOOL_ROUNDS`, and no round count — the single thing the token audit found to be the chat agent's entire cost driver. One structured-output call, always one round, ~1.100-token prefix.
The **only** thing shared is `agent_tools.build_time_context()`'s header. "Resolve Friday to a date" is genuinely the same problem with the same already-debugged answer (hand the model a date map rather than let it do calendar arithmetic), and a second copy would mean two versions of "today" to keep in step. `AGENT_WRITABLE_FIELDS` was deliberately NOT widened for the new agent's extra fields — `/agent/confirm-action` re-checks the chat agent's proposals against that constant, so widening it there would have silently widened the chat agent's write surface too; the new agent has its own superset.

### Decision: the per-task agent plans, the app writes
`POST /tasks/{id}/agent-edit` returns a validated field diff and writes nothing; `TaskCard.jsx` applies it through the same `onUpdate` its manual Save button uses. The alternative — writing inside the endpoint and returning the updated task — saves one round trip and was rejected: the existing PATCH/DELETE path already carries reminder invalidation, calendar sync and the origin-aware delete reporting, and a second write path is a second place for all of that to drift. It grants no new privilege either, since the user can already PATCH their own tasks from the same screen. The agent fills in the form; the form still submits itself.
Related: **applied immediately with UNDO, not preview-then-confirm.** Every field change here is reversible, so a confirm click on each edit is a permanent cost paid against a mistake that is already takeable-back, and it would make the agent slower than the manual fields it is meant to beat. `before` is built server-side from what the database actually held, so undo restores real previous values rather than a stale card's. **Delete is the exception**: it is a hard delete with no undo, so it always routes into the card's existing confirm-and-delete flow.

### Decision: the answer's LANGUAGE is chosen in code, not asked of the model
`task_agent.answer_language(instruction)` looks for Greek script in the instruction and the prompt then STATES the language ("Write "message" in Greek.") instead of asking the model to match it. Measured twice on a prompt where this should have been easy: **the model writes in the language of the TASK, not of the instruction.** Every task in this app is Greek, so an English instruction came back answered in Greek — with the rule in the instruction's FIRST line, in an instruction a twentieth the size of the chat agent's. Wording it harder made it worse in the other direction: "an English instruction gets an English message even when the task is Greek" flipped every GREEK answer to English, which is the language the owner actually uses. Both directions reproduced 2/2.
This is the same lesson as the 2026-08-06 overhaul, in a case where the usual escape hatch was already exhausted: **a rule the code can enforce does not belong in the system instruction.** Language is knowable before the call, so it is not the model's decision to make. Detection is deliberately crude — any Greek character anywhere means a Greek answer — because a Greek user typing one English word getting Greek back is the right direction to fail in.
**This contradicts the standing explanation for the chat agent's Gap 3** ("an English question is answered in Greek"), which CURRENT_TASK.md blamed on the rule sitting in the last line of a ~7.800-character instruction and proposed to fix by moving it up. That hypothesis does not survive this result. The same fix — decide it in code, state it as a fact — is the one to apply there, and moving the line is not worth trying first.

### Decision: the UX is designed for people who did not build the app
Settled 2026-08-09, before the redesign in FEATURES.md was drawn. The app has one real user and a hardcoded `OWNER_USER_ID`, but the intent is to put it in front of others, and that single answer settles arguments that are otherwise matters of taste: **icons need words** (a grey gear floating over a task list is legible to its author and to nobody else), **errors must be visible** (`console.error` is not a user interface), **defaults must be safe** because most people never open settings, and **density is not free** — the owner could read a six-element metadata row because he knew what the six elements were. Where the redesign rejected an option, this is usually what rejected it. If the app is ever deliberately made single-user again, these trade-offs are the ones to revisit first.

### Decision: one copy of any server object the UI can write
App settings lived in four independent `useState` copies and `PATCH /settings` writes the whole object, so two toggles in one sitting silently reverted each other (full account in FEATURES.md). The rule that came out of it: **a server object the UI can WRITE gets exactly one owner in the client**, and everything else reads it from there. Applied to app settings (`AppSettingsProvider`) and to the profile (fetched once in `App.jsx`, previously re-fetched by `SettingsModal` on every open). It is also why `updateSettings` merges through a ref rather than a captured closure — a stale closure rebuilds the same bug one component further in. The regression test asserts the OLD model fails as well as the new one passing; a test that only exercised the fix would pass just as happily against a store that never worked.

### Decision: nothing in the UI is encoded by colour alone, and colour is spent only where it means something
Two halves of one rule, both from the redesign. Priority was an 8px dot in red/amber/blue — the classic confusion set — and now carries its P1/P2/P3 text as well. In the other direction, dates are coloured **only** when overdue or today: a list where every date is coloured is a list where colour has stopped carrying information. The same reasoning is why `OptionSheet` marks the current choice with a tick rather than a coloured row.

### Decision: a control must never look disabled and act anyway
The task row's reminder and calendar-sync buttons rendered at `opacity-40` when the task had no `due_time`/`due_date` and stayed clickable, answering with a toast explaining why they could not work. Forty percent opacity means disabled everywhere. A control that contradicts its own appearance does not confuse the user about the feature, it confuses them about the interface. The fix is now the pattern: **either it is genuinely disabled and says why (`Switch`'s `disabledReason`), or it is not rendered at all** — the row draws the reminder and sync indicators only when they are actually on.

### Decision: every gesture has a visible equivalent, and no gesture is destructive on its own
Swipe right completes a task; swipe left **reveals a tray** rather than acting, so Reschedule and Delete each need a deliberate second tap. Both live in the `⋯` menu regardless, which is the accessible path — a gesture with no visible equivalent excludes everyone who cannot perform it, and the first-use hint is therefore about speed, not access. ~~The design draft had promised an undo toast on delete; deletion here is a hard delete (see the per-task agent decision above, which already routes delete into the confirm dialog for exactly this reason), so the design was corrected instead of the toast being made to lie.~~ **CORRECTED 2026-09-04** — true when written, false now: deletion stamps `deleted_at` and the row survives. What the design draft wanted exists, in a different place: the **Επαναφορά** button in Browse's History tab rather than an undo on the toast. The confirm dialog stays anyway — it is cheaper to answer a dialog than to go find the task again — and so does the tray's second tap. Gesture safety comes from a direction lock plus `touch-action: pan-y`, which leaves vertical scrolling with the browser.

### Decision: local filtering beats the agent wherever the answer is not a judgement
Task search filters in-memory over tasks `App.jsx` already holds — no request, no debounce, no tokens — where previously the only text search in the app was the AI agent, spending a model call and a round trip on a substring match. The same reasoning kept quick-reschedule (today/tomorrow/next week) as arithmetic rather than the agent chips that offer the identical three. The dividing line is not "cheap vs expensive", it is **whether the question needs judgement**: "move it to the Wednesday after the holiday" is the agent's, "tomorrow" is not. Client search deliberately does NOT copy the agent's exact→word→stem ladder; that ladder exists because a model gets one shot per round, whereas a typist corrects a near-miss with the next keystroke and a stemmer would return surprising matches with nothing on screen to explain them. Greek folding (NFD accent stripping and manual final-sigma normalisation) is the part that actually matters and is covered by tests.

### Decision: the theme is an attribute JS resolves, not a media query
The Appearance setting (2026-08-08) made the app able to disagree with the OS, and that forced a choice about where dark mode lives. It is now a single `<html data-theme>` attribute holding the RESOLVED theme, written only by `frontend/src/utils/theme.js`; `index.css` keys the dark palette off that selector and there is deliberately **no** `@media (prefers-color-scheme: dark)` copy of the block.
**The alternative — keep the media query and add `[data-theme=dark]` beside it — was rejected twice over.** It means two definitions of the same 47 tokens, so a token added to one and forgotten in the other silently falls back to its LIGHT value: one unreadable element on an otherwise correct dark screen, the kind of thing that only ever shows up on someone else's phone. And when the two disagree — which is the entire point of the feature — they fight. CSS cannot express "the OS setting, unless the user overrode it", so the resolving happens in JS and CSS is left with one plain attribute to match. The cost is that the palette now needs JS to apply, which is acceptable in a React app that renders nothing at all without it, and `index.html` carries an inline pre-paint script so there is no white flash. That script duplicates the storage key and the resolution rule on purpose (anything imported is already too late); `scripts/theme.test.mjs` runs both implementations over every (preference × OS) pair and compares them, so the duplication cannot drift in silence. `ui-check.mjs` separately asserts that the two palettes define the same token set, in both directions.
**Two consequences that are not optional.** `initTheme()` must listen for OS changes, because "System" is resolved once at load and phones flip themselves at sunset — without the listener it means "the system, as of whenever you last opened this". And anything that follows `prefers-color-scheme` on its own has to be repointed at the attribute or it will contradict the setting: the `theme-color` metas (rewritten by `applyTheme`), `color-scheme` (declared per theme so native controls follow), and Tailwind's `dark:` variant (`@custom-variant` — no users today, but one stray class away from a bug this app has already had once).
**Stored in localStorage, not in `app_settings`.** It follows the Language switcher, for the same reason: it is a property of the device you are reading on, not of the account. A server-side value would force a phone in bed and a laptop at a desk to agree.

### Decision: Hostaway multi-tenancy deferred to "year 2" — SUPERSEDED 2026-08-14
The original entry read: *"Only the owner has Hostaway now. `get_user_id_for_hostaway_account()` is the single 'one door' to change when others connect their own Hostaway accounts later. Nothing else needs rewriting."*

Year 2 arrived early, and **the prediction was half right**. The one door was indeed the only place that decided *who* a message belonged to — but replacing it was not a one-function change, because the answer stopped being singular in two different ways at once:
- **One accountId now maps to MANY users**, not one. Fifteen staff share the owner's Hostaway account. So the call site could not simply take a different user_id back; the webhook had to become a loop, and everything expensive inside it (the classification, the enrichment) had to be hoisted out so N colleagues do not cost N Gemini calls.
- **Credentials stopped being global.** `HOSTAWAY_CLIENT_ID`/`SECRET` came from `.env` and the access token lived in one module-level variable. With two accounts connected, that variable hands one user's token to the other's requests. Every Hostaway function signature changed to take `HostawayCredentials`, which is what actually rippled through `main.py` and `services.py`.

What the entry got right is that nothing *else* had to be redesigned: threading, the reply poller's decisions, escalation and the deep link were all untouched. See `docs/superpowers/specs/2026-08-13-hostaway-per-user-integration-design.md`.

### Decision: token usage has a single source of truth
`token_usage_log` is per-user; usage summaries are computed by summing it. No cached usage column on `profiles` (two sources would drift). A future `profiles.monthly_token_quota` + Stripe billing is deferred (see BACKLOG).

### Decision: profiles table for per-user profile/settings, not auth.users
Supabase's `auth.users` is off-limits for custom fields, so a `profiles` table (1:1, auto-created on signup) holds display_name/email and is the right home for future per-user settings.

### Decision: Settings sections collapse independently, closed by default, hidden-not-unmounted
Each of Settings' seven sections (My Profile, Notifications, Google Calendar, Language, Developer, Account, About) is now a collapsible accordion row (`CollapsibleSection`), all closed the moment the modal opens. Rationale: the long single-scroll modal was unusable on mobile once My Profile + Settings redesign added more sections. Independent toggles (not one-open-at-a-time) were chosen over a strict accordion so the user can compare two sections at once (e.g. Notifications and Calendar) without losing either's state. Collapsed content is hidden via a CSS class, not unmounted — this preserves in-progress form state (e.g. a partially typed display_name) across a collapse/expand and avoids re-running a section's own data-fetching effects every time it's re-opened. This supersedes NOTHING — FEATURES.md's "single scrollable modal, not sub-page navigation" characterization of Settings still stands; this only changes each section from always-expanded to collapsible within that same single modal.

### Decision: docs/knowledge workflow (this restructure)
State lives in /docs (single source of truth), not in long chats. One task = one chat (cost grows quadratically within a chat). The Project indexes ONLY /docs, never code. Retrieval is semantic search over chunks; cold-start uses rare anchor strings. Facts are never hardcoded in the system instruction (they drift); the only deliberate exception is the hosting/workflow SHAPE.

### Decision: measure the agent's token cost before optimizing it
An optimization proposal (implicit caching, a pre-loaded day view, compact tool results, merging the propose_* tools) was reviewed and NOT adopted as written, because every figure in it was inferred rather than observed. A read-only query over existing token_usage_log rows then established, before any code was written: thinking tokens are zero (so a thinking-budget change is off the table entirely); input is ~90% of tokens and ~77% of cost; the fixed per-round prefix is ~1,830 tokens; the average call is ~4,264 tokens, and the "16k" figure that prompted this work is the tail, not the typical case. Cost scales with the NUMBER OF TOOL ROUNDS.
Two constraints on any future work, from the same review: (a) the tool result is appended to `contents` and therefore re-sent on every subsequent round, so compacting it saves proportionally more the more rounds a question takes; (b) implicit caching and round-reduction are substitutes, not complements — removing a round also removes the cache hit that round would have produced, and at a ~1,830-token prefix the app sits near the minimum input threshold implicit caching requires, so caching may never engage at all. Supersedes nothing.

### Decision: agent instrumentation is log-only; token_usage_log writes are unchanged
Per-round and per-run token figures (including thinking and cached counts) go to the application log only. They are deliberately NOT passed to `token_tracker.log_token_usage()`. Rationale: a write to `token_usage_log` containing a field with no matching column is rejected wholesale and silently breaks ALL token logging (documented in DATABASE_SCHEMA.md) — and this change exists precisely to make measurement reliable. Persisting thinking/cached counts is a separate task requiring a migration first.

### Decision: agent search results sort chronologically, not priority-first
`search_tasks` sorts by (due_date, due_time, priority) before capping. The cap's purpose is "the next N things to do", and a P1 due next week is not more urgent than a P3 due today. Consequence: a high-priority far-future task can fall outside the cap; the `truncated` flag tells the agent to mention that more matches exist.
Supersedes nothing (there was previously no sort at all — an arbitrary subset was kept).

### Decision: one open-task predicate, changeable in exactly one place
`agent_tools.is_open_task(t, include_completed=False)` is now the only place "counts as an open task" (not rejected, approved, and not completed unless asked) is decided — the `search_tasks` main filter, the `overdue_count` computation, and the `no_matches_hint` lookup all route through it instead of each carrying its own inline copy of the same three-condition check. Rationale: the pending-approval policy is a product decision that is still open (see CURRENT_TASK.md) — when it changes, it must change in one function, not require re-auditing every place the three fields were checked inline. Supersedes nothing (there was previously no single predicate, just duplicated inline checks).

### Decision: the round ceiling degrades gracefully instead of raising
Previously, exhausting `MAX_TOOL_ROUNDS` raised a `RuntimeError` that surfaced to the user as a failure — meaning the single most expensive run (every round used) was also the one guaranteed to look broken. It now makes one additional tool-less call, explicitly told to answer NOW from whatever was already found, and returns that answer instead of an exception; only a still-empty final answer raises. This is logged as `outcome=max_rounds_recovered`, deliberately distinct from `outcome=ok` — the run still signals that something went wrong (too many rounds needed), the user just no longer pays for it with a 500. A partial, honest answer beats an exception. Paired with lowering `MAX_TOOL_ROUNDS` from 6 to 4: without this decision that change would only have surfaced the error more often; with it, the worst case gets cheaper and still answers.

### Decision: calendar arithmetic is resolved in Python, never computed by the model
Weekday names ("Τετάρτη", "Monday") and the "overdue" date bound are both calendar arithmetic — exactly the kind of thing a language model does unreliably. Rather than asking the model to compute "next Wednesday" or "yesterday" from a stated today-date, the actual dates are resolved once per request in Python (`agent_tools.build_time_context`) and handed to the model as a `[Next 7 days]` lookup table in the user turn; the model's job is to READ the answer, not calculate it. Supersedes nothing — this generalizes the existing single-clock-read design (previously only `today_iso` for the today/overdue checks) to also cover weekday resolution.

### Decision: implicit caching is NOT available — the only cost lever is a smaller prefix
**Measured, not assumed** (2026-08-02, `gemini-3.1-flash-lite-preview`): three byte-identical back-to-back `ask_agent()` calls all reported `cached=0`, and a raw `generate_content` response contains **no cache field at all** in `usage_metadata` (`cached_content_token_count` is absent, not zero). Implicit caching does not engage for this model at this prefix size, full stop.
Consequence: an earlier proposal to make `build_system_instruction()` static (removing the per-minute `now_hhmm` interpolation, which does make the prefix change every 60s) was **dropped** — it was justified entirely by unlocking caching, and there is no caching to unlock. It buys ~30 tokens of de-duplication for a reword of TIME AWARENESS that cannot currently be verified against real data (the owner account has no timed tasks due today). Revisit only if Google enables caching for this model.
Therefore the ONLY lever on per-round cost is **making the prefix itself smaller**. Measured breakdown per round, before the compression below: system instruction 2.473 tokens (60%), read tools 477, propose tools 762 (18%), day view + header + question ~400. Total fixed prefix 3.712 tokens, paid raw on every single round.

**Re-confirmed at scale, and the dropped change was made anyway (2026-08-07).** An A/B of the two instruction forms over the same synthetic 23-task dataset — 26 identical questions per arm, 52 runs, 257 rounds — produced **zero** cross-request cache hits. The only non-zero `cached_content_token_count` ever observed in the whole exercise (4.041 tokens) was round 4 *within* a single request, where the instruction is built once and cannot change. Bigger sample, same conclusion: there is no caching to unlock on this model.
`build_system_instruction()` was nonetheless made static (it now takes no arguments and returns a constant), for the one reason the original rejection left open: it *"cannot currently be verified against real data"* — it now is, across a 26-case acceptance suite. Prompt tokens moved **-0,4% across the 26 identical questions, i.e. noise**. Nobody reading this should expect a token win from it; it is de-duplication (the date and time already reach the model via `[Now:]` and the day view's pre-computed passed/upcoming) and a prerequisite that costs nothing, not an optimization.
**Process note, worth more than the change itself**: this was proposed as the single biggest cost lever available, by someone who had not read this decision first. It cost ~400k tokens of A/B testing to re-derive a conclusion already written down here in one paragraph. Read DECISIONS.md before proposing an agent optimization — every obvious idea has probably already been measured.

### Decision: the system instruction is compressed and de-duplicated, not appended to
The instruction had grown to 10.532 characters / 2.473 tokens across 14 sections, because every behavioural bug was fixed by appending prose — and that prose is taxed on every round of every request forever. Rewritten to 6.092 characters / **1.490 tokens (-40%)**, cutting the fixed prefix from 3.712 to **2.729 (-26%)** and measured end-to-end at **-23% total tokens on every acceptance test**, with zero behavioural regression (identical round counts and correct answers across all 9 read tests).
What was merged: `SEARCH SCOPE` + `CATEGORY MATCHING` + `FILTER DISCIPLINE` + `KEYWORD SEARCHES ARE FUZZY` → one `FILTERS` section; `UNDATED TASKS` + `RESULT LIMITS` + `NO MATCHES` → one `RESULTS` section. This was not only compression — `CATEGORY MATCHING` ("Do not leave category empty out of caution") directly contradicted `SEARCH SCOPE` ("Otherwise leave it empty"), and the contradiction was live in production (see below). Rule of thumb going forward: a new behavioural rule belongs INSIDE an existing section, and if it contradicts one, the old one is what's wrong.

### Decision: a name lookup passes keyword only, and retries with include_completed
Two production bugs found by running the acceptance list directly against `ask_agent()` (2026-08-02):
1. **Invented filters survived on the write path.** "σημείωσε το <task> ως ολοκληρωμένο" produced `search_tasks(date_from=today, date_to=today, category=Personal, keyword=...)` — neither the date nor the category came from the user. The `SEARCH SCOPE` rule was working for read questions but being overridden here, most likely by `CATEGORY MATCHING`'s "do not leave category empty" plus `DATE RESOLUTION`'s single-day rule bleeding into a request with no date at all. Fixed by the merge above plus an explicit rule: *looking up a task the user NAMED in order to act on it is a name lookup — pass keyword ONLY, never a date or category you inferred rather than heard.*
2. **`include_completed` was never used.** Nothing told the agent to retry with it, so an already-completed task was reported as "I couldn't find that task" — a wrong answer, produced at the most expensive path in the whole suite (3 rounds, 13.017 tokens). Fixed by an explicit rule to retry ONCE with `include_completed=true` before concluding a named task does not exist. Now 2 rounds, 6.545 tokens, and the correct answer ("it is already completed") — **-50% and correct**.
Both are the same underlying failure mode the project has now hit three times: two instructions that disagree, with the model picking whichever it likes. Supersedes nothing; tightens "the agent never invents search filters".

### Decision: the agent never invents search filters it was not given
Production logs showed the model adding category and priority filters to a question that contained neither, and inventing a 7-day window for a question with no time reference. Both returned plausible answers over silently narrowed data. Filters are therefore constrained explicitly in the system instruction, and an over-broad search is preferred to a narrowed one. Related: the [Next 7 days] map is a lookup table, never a search range. Supersedes nothing.

### Decision: the pre-loaded day view is NARROW — today + overdue only, not a week
Measured baseline: every agent question costs exactly 2 rounds (1 search + 1 answer) at ~3,350 tokens/round, and the round count is the entire cost driver. Pre-loading today's and overdue open tasks into the first turn removes that lookup round for day-scoped questions (~7,000 → ~3,600 tokens for reads, ~10,700 → ~7,100 for writes on today's tasks). A 7-day horizon was considered and rejected: measured cost is ~130–165 tokens per task, so a week-wide injection would cost ~2,000–2,500 tokens on EVERY single request to save ~3,350 on only the minority that actually ask about the coming week — the wrong trade in the opposite direction from what this whole effort is trying to achieve. Supersedes "today-scoped searches report an overdue COUNT, not the overdue tasks" (moved to DECISIONS_ARCHIVE.md) — the day view lists the actual (capped) overdue tasks at no extra round, making a count-only mechanism pointless; having both would also mean two mechanisms answering the same question, which is exactly the shape of bug the previous PR (invented search filters) had to fix.

### Decision: day-view overdue/pending sections are capped with an explicit overflow line
Overdue tasks accumulate without bound in a real to-do app (nothing removes them from "overdue" except completing or rescheduling them), so an uncapped section would improve the AVERAGE per-request cost while making the WORST case unbounded — the opposite of this PR's goal. `DAY_VIEW_OVERDUE_CAP` (10) and `DAY_VIEW_PENDING_CAP` (5) bound both sections; a "(+N more ...)" line tells the agent (and, via its answer, the user) that more exist rather than silently truncating. `TODAY` is deliberately NOT capped — a single day's tasks are bounded by nature. Supersedes nothing.

### Decision: tasks pending approval get their own day-view section instead of being made "open"
Tasks awaiting Inbox approval (mostly AI-extracted or Hostaway webhook tasks) are NOT "open" — `is_open_task()` correctly excludes them, and that meaning is unchanged. But a Hostaway task escalating today while completely invisible to "what do I have today?" is the worst failure mode for the actual business this app supports (a real Airbnb/short-let operation where those escalations matter). `is_pending_task(t)` is the single source of truth for this separate policy — not rejected, not completed, `approval_status` false — and the day view surfaces pending tasks due today or already late in their own PENDING APPROVAL section, explicitly NOT merged into OVERDUE/TODAY, with the system instruction telling the agent to describe them as awaiting approval and never propose a write on one. Supersedes nothing — this is a new, additive surface, not a change to what "open" means.

### Decision: agent memory is server-reconstructed, bounded, and answers-only
Replaying raw tool results would multiply the cost the day view was built to reduce: a tool result is appended to `contents` and therefore re-sent on every subsequent round WITHIN a request (see "implicit caching is NOT available" above), so replaying it across turns TOO would compound that same cost again. Questions and final answers are small and do not compound the same way. The client sends only a `conversation_id`, never the messages themselves, because a client that sends its own history controls both the prompt shape and the bill; the backend enforces `HISTORY_MAX_PAIRS` (4 pairs / 8 messages), `HISTORY_MSG_MAX_CHARS` (500) and `HISTORY_MAX_REFS` (5) regardless of what a client would send. Same shape as `/agent/confirm-action` being the actual write boundary rather than trusting the client's echoed proposal.
This IMPLEMENTS the BACKLOG item "Agent multi-turn memory". It REFINES (does not supersede) "agent is stateless per question; only filtered results reach the LLM" above — the agent is still stateless with respect to tool results, and still re-loads and re-filters all of that user's task data fresh on every single request; only the visible conversation TEXT (questions + final answers) now persists and is replayed, bounded and server-enforced.

### Decision: history resolves references only, never supplies task facts
History may be stale by minutes or hours — nothing re-verifies an earlier answer before replaying it. Task facts therefore always come from the fresh day view or a fresh tool call in the CURRENT turn, never from what an earlier answer said; history exists solely to resolve references ("it", "that one", "change it to Friday"). A `[refs: name=id]` line in an earlier answer is a legitimate record_id source — it came from a real tool result earlier in the same conversation — but it is not exempt from validation: it still has to match a task in the current, freshly-loaded, user-scoped task list before `propose_update_task`/`propose_complete_task` will act on it, and is re-validated again server-side by `/agent/confirm-action`. A deleted or since-changed task simply fails that validation and the agent falls back to `search_tasks`. Ambiguous follow-ups (e.g. "set it to 5" — day of month or hour?) are clarified with a question, never guessed, because a guessed value would appear on a confirmation card the user may accept without reading closely. Supersedes nothing.

### Decision: one table (agent_runs) is both the debug archive and the memory source
Agent behaviour is verified by asking real questions and checking whether the model called the right tools — but Render's application logs are ephemeral, so a verification pass run against them leaves nothing behind and has to be redone from scratch. Persisting each run — including the exact first-turn text the model saw and every round's tool calls — turns verification into a SQL query and makes a wrong answer diagnosable after the fact: you can see what the model had in front of it, not just what it replied. Full text is stored because it costs ZERO tokens (nothing in this table is ever sent to the model) and a few KB of storage.
A separate `agent_messages` table was created and then dropped before use: one row of `agent_runs` already IS a question/answer pair, so a second table would have stored the same text twice and created a second source of truth. `repository.get_recent_agent_runs` now reads the same table `log_agent_run` writes — the debug archive and the bounded conversation memory (see "agent memory is server-reconstructed, bounded, and answers-only" above) are the same write and the same rows, not two parallel systems that could drift.
Constraint: this table is diagnostic + memory only and is never summed for usage or billing; that remains `token_usage_log`, per "token usage has a single source of truth". The insert builds its column list explicitly rather than splatting a dict, per the documented failure where one unknown field silently broke all token logging.
Also: the agent chat's starter chips are read-only questions only — no "Add a task" chip, because creating a task via the agent costs a proposal round for what the add-task form does for free. Supersedes nothing.

### Decision: a rule the code can enforce does not belong in the system instruction
Five behaviours were failing in live testing (3 of 10 questions, 2026-08-06), and every one of them had already been "fixed" once by appending prose to the system instruction. That is why they came back: the instruction had grown to 7.4k characters, is paid on every round of every request, and the model demonstrably drops individual lines from it. The clinching evidence: `"τι πρέπει να ψωνίσω;"` appears in the instruction VERBATIM as a worked example showing exactly which filters not to pass, and the model still passed all three of them.
The rule going forward: if code can enforce it, code enforces it, and the prose comes OUT. Applied to — the pending-approval write ban (now refused in `propose_complete_task`, `propose_update_task` and `/agent/confirm-action`; previously it existed ONLY as one instruction line, so an approval bypass was one dropped line away and nothing in the codebase would have stopped it); the `include_completed` retry (now done inside `search_tasks`, was costing a full round every time a named task was already completed); the enumerated `propose_update_task` field list (duplicated the SDK-generated schema, which the model cannot violate anyway); the duplicated record_id rule (already enforced by `_find_task`).
Supersedes nothing, but it REVERSES the working assumption behind "the system instruction is compressed and de-duplicated, not appended to" — that decision said a new rule belongs INSIDE an existing section. This one says the first question is whether it belongs in the instruction at all.

### Decision: a tool result carries its own instructions, next to the data
`truncated: true` was observed being silently dropped: the rule telling the model to report it lived ~40 lines away in the system instruction, disconnected from the moment the model actually reads the number. The fix that worked — already proven by the pre-existing `no_matches_hint` — is to attach a short, numbers-filled instruction to the result itself, computed from that call's own data.
Now standard for every result-shaped signal: `truncated_hint`, `undated_hint`, `fuzzy_keyword_note`, `completed_only_note`, `over_filtered_hint`. A hint that RETURNS THE ROWS beats one that describes them: measured in the same test run, the fallbacks that hand back data (`completed_only_note`, `fuzzy_keyword_note`) resolve in 2 rounds, while `over_filtered_hint` in its describe-only form cost 3-4 because the model had to run a second search to fetch what the first call already held. `over_filtered_hint` therefore also returns `relaxed_matches`.
Constraint: hints are additive fields on the result, never a replacement for the honest `tasks`/`total_matches` of the query as asked. An over-filtered search still reports 0 matches for the filters it was given; the relaxed rows arrive alongside, labelled.

### Decision: filter examples show the WHOLE call, with nulls written out
The FILTERS section listed only the arguments to pass, with a negative aside ("NOT Personal, NOT P3, NOT today"). That is the formulation the model ignored on a verbatim-matching question. Rewritten so every example spells out EVERY parameter including the ones that stay empty (`keyword="ψώνια" category=null priority=null date_from=null date_to=null undated_only=false`), turning "not mentioned" into a value the model must actively produce rather than a field it can quietly fill in — positive instruction instead of negative.
Measured before/after on the same live questions: invented filters dropped from 6 occurrences to 1 across 29 questions, and the five questions that had been costing an extra round each stopped doing so (-11% total tokens across the suite, -70% on the worst single case). Verified separately that this did NOT over-correct into writing null everywhere: a 15-question category/priority matrix (including the synonyms "δουλειές" → Business, "μηνύματα από επισκέπτες" → Hostaway, "σημαντικά" → P1, and repeats for stability) set the right filter 14/14 times, with the one nominal failure being a question correctly answered from the day view with no search at all.
This is the counter-example to the decision above: prose CAN work, but only when it states the required output shape rather than forbidding a wrong one. Supersedes the example format introduced with the FILTERS/DATE RESOLUTION merge.

### Decision: Greek inflection is handled by prefix stemming, not a real stemmer
A task named "Ραντεβού οδοντιάτρου" was invisible to a search for "οδοντίατρος": the match is a literal substring and Greek inflects the ending. No instruction and no larger model can fix a tool that never returns the row. Greek changes word endings and never word starts, so `stem_words()` compares a 5-character accent-folded prefix per word (words under 6 chars are dropped rather than stemmed — a 5-char prefix of a short common word matches nearly everything).
It joins the existing exact → word-level fallback chain as a third tier, so it is only consulted when the exact pass returned nothing, which contains the over-matching this deliberately loose comparison would otherwise cause.
Explicitly NOT the right long-term answer: Supabase is already PostgreSQL, whose bundled Snowball dictionaries include Greek, so `to_tsvector('greek', ...)` is the correct fix and would also fix stemming inside descriptions properly. This buys the common case with no schema change and no per-query round trip. Revisit when the logs show word-level matching firing often.

### Decision: the filters the agent searched with are shown to the user
Every other guard against invented filters is the agent policing itself. The agent was observed answering "you have none" over a search it had narrowed with a category and a date the user never mentioned — and the narrowing was completely invisible. `/agent/query` therefore returns the filters of each `search_tasks` call it made, and the chat renders them under the answer ("Έψαξα: σε Business, από 2026-08-06 έως 2026-08-13 · 1 βρέθηκαν").
This does not prevent an invented filter; it makes one impossible to miss, because only the user knows what they actually meant. Same principle as the confirmation cards: show the machine's intent before it matters instead of asking to be trusted. This is also how production tools solve it — Todoist's Filter Assist has the LLM emit a filter query that the user then SEES and can edit, rather than searching on the user's behalf invisibly.
Only filters actually passed are listed; rendering an omitted filter as a constraint would be its own lie.

### Decision: a scope the tools cannot express is a missing parameter, not a prompting problem
"Τι έχω χωρίς προθεσμία;" had no expressible form — `search_tasks` could filter BY a date range but not FOR the absence of one. The model compensated by searching category by category looking for undated rows: 5 rounds and 27.919 tokens for a one-line answer, the single most expensive observed run in the suite. Adding `undated_only` made the same question 2 rounds and 8.271 tokens (-70%).
Generalises: when the model takes an obviously roundabout path, check first whether the direct path exists in the tool surface at all. `undated_only` overrides `date_from`/`date_to` rather than combining with them, since "no date" and "a date range" are contradictory and silently returning nothing would be the worst reading of the two.

### Decision: a follow-up write must target a task the CONVERSATION named, enforced in the tool
The worst agent bug found so far, and it was invisible until someone repeated the same two turns six times. Ask "πότε είναι το ραντεβού στον οδοντίατρο;" and then "άλλαξέ το για την Παρασκευή", and the agent proposed the update against **"Επισκευή αυτοκινήτου" — the first row of the pre-loaded day view** — 4 times in 6 on the current instruction and 2 in 6 on the previous one. Confirming that card edits a task the user never referred to. The `[refs: name=id]` line carrying the correct record_id was in context and ignored, and CONVERSATION HISTORY already said in as many words *"never from whichever task in the day view looks most salient"* — so this is the fourth instance of the same lesson: more prose was never going to fix it.
Two changes, both moving the rule to where the model actually operates:
1. **`_unjustified_target()`** in `build_write_proposal_tools` refuses a target that is neither a record_id this conversation has already surfaced nor a task the user names in the current turn — the latter decided with the same `stem_words()` matching `search_tasks` uses, so Greek inflection works. Deliberately **not** an anaphora detector: "το" is also the commonest Greek article, and this module avoids fragile Greek/English regexes on principle (see the day-view injection rationale). Armed only once the conversation HAS refs, i.e. on a follow-up turn, so single-turn behaviour is untouched.
2. **`build_conversation_refs_block()`** puts those tasks in the CURRENT user turn, above the day view, instead of leaving them at the tail of a replayed answer where they were demonstrably not read. ~64 tokens, and only on follow-up turns. Same principle as the day view and as `truncated_hint`: the data goes where the model reads it, at the moment it reads it.
Measured after both: **0 wrong writes in 5** (was 4 in 6), 4 correct proposals and 1 clarifying question that names the right task. Note the split — the guard alone converted wrong writes into safe *questions* (still 2 rounds); it took the refs block to get correct *answers*. Refuses-and-asks is the floor, not the goal.

### Decision: a field value copied from another task is refused, not just the wrong target
Immediately after the guard above stopped the model targeting the wrong task, it started targeting the RIGHT one with the wrong task's data: asked to move the dentist appointment to Friday it sent `due_date` (correct) **plus the car repair's `description`**, which a confirmed card would have written straight over the appointment's own. This passed the first test run, because that assertion checked only *which* task was hit, not *what* was sent — the test was the bug.
`propose_update_task` now refuses a `description` or `task_name` that is character-for-character another task's current value: that is a copy, not a change anyone asked for. Enum fields (`priority`, `category`) are excluded — two tasks sharing a priority carries no such signal. Complements the existing no-op dropping, which handles a field re-sent at its OWN current value; this handles one re-sent at a DIFFERENT task's.
Measured after: 4 proposals in 5 carrying `due_date` and nothing else, 1 clarifying question, 0 contaminated writes. **Cost**: the model recovers by calling `get_task_details` and re-sending, which takes the run from 2 rounds to 4 — landing exactly on `MAX_TOOL_ROUNDS`. Scope is narrow (7 blocks in 282 test runs; 90% of runs never call `propose_update_task` at all, and the explicitly-named update case was never blocked once in 5 runs), but if it ever needs a fifth round it falls to the tool-less recovery answer. The cheaper variant — DROP the contaminated field with a note instead of returning an error, matching how no-ops are already handled — is the obvious next step and is unverified.

### Decision: blocking endpoints run in the threadpool, not on the event loop
All 27 FastAPI endpoints were `async def`, but every body is fully synchronous: Supabase queries, Gemini `generate_content`, Google Calendar, web-push — plus `time.sleep(2 ** attempt)` in `agent_engine`'s retry path. An `async def` endpoint runs directly on the event loop, so each of those calls blocked the entire server for its full duration; for `/agent/query` that is a 2,5 s median and a 5,3 s maximum during which nothing else could be served. Invisible with one user, and a queue with two.
23 of them are now plain `def`, which is what Starlette runs in its threadpool. No body changed and single-request behaviour is identical — this is purely concurrency. Left `async`: `extract_voice` and `extract_image` (`await UploadFile.read`), `hostaway_webhook` (`await Request.json`), and `health_check`, which performs no I/O at all and so is genuinely better off on the loop.

### Decision: a refusal is data, and "not decided" is a third state
(2026-08-23) A proposal the user CANCELS is recorded, as its own row in `agent_action_decisions`, and a proposal nobody touched is recorded by its **absence** — reported as `undecided`, never as a cancellation.
**Why the refusal at all**: `agent_runs.proposed_actions` recorded what the agent proposed; nothing recorded what the human then did. Confirm executed the write and left no trace it came from the agent (the sole exception being `complete_task`, which sets `completed_source = 'agent'`), and **Cancel never reached the server** — purely local state in `AgentChatModal.jsx`, so the card greyed out and that was the end of it. That threw away the sharpest signal this app can collect about the agent's judgement: the model proposed something and the human refused it. It is the same signal `is_rejected` preserves for the extractor's suggestions, and the same reason `ai_suggested_category`/`ai_suggested_priority` are frozen on every task — the machine's guess has to survive the human's correction, or there is nothing left to learn from. The very first real row already showed the agent guessing at a referent it had just said it was unsure of, and the guess being refused.
**Why undecided is not cancelled**: walking away from a card is a different fact from refusing it. Collapsing the two would fill the refusal set with cards the user merely never got to, and poison the signal the table exists to collect. This is why decisions are their own rows rather than a column on `agent_runs` — a run row is written once, when the answer is produced, and the decision arrives later, sometimes never.
**Cost accepted**: the table records THAT a proposal was refused, not WHY. A refusal because the agent picked the wrong task and one because it set a time the user did not want are indistinguishable in the data.
The recording never raises and the client never awaits it: it runs after a write that already succeeded, so an audit failure must not surface as an error on an action that worked, and refusing a card must stay instant.

### Decision: the two Hostaway auto-close gates stay, with their cost known
(2026-08-23) The owner reported that replying to a guest had "stopped closing tasks". It had not: measured over 39 tasks across the ten days after the feature was verified, **detection is exact** — every human reply that arrived while its task was open was recorded, zero misses. What blocks the close is two rules he had chosen himself: **`HOSTAWAY_REPLY_AUTOCOMPLETE_PRIORITIES = {"P3"}`** (6 cases) and the **ambiguity rule**, which completes nothing when one reply answers several open tasks of one conversation (11 cases). Shown both, with the numbers, he chose to **keep both unchanged**.
**The cost, recorded so it is not rediscovered as a bug**: the ambiguity rule compounds. Nothing closes what it blocks, so open tasks accumulate within a conversation — two of them reached seven — and once a conversation holds more than one open task, no reply in it can ever auto-close anything again. The auto-close rate therefore falls over time by design, not by defect. Anyone reading a future report of "it stopped working" should measure detection and completion **separately** before touching code: they fail for entirely different reasons, and last time nothing was wrong with the code at all.

### Decision: stored third-party secrets are encrypted, and what that does NOT buy
A Hostaway client secret is not a password to this app — it is full API access to someone else's property management system: reservations, guest names, emails, phone numbers. `google_calendar_connections` stores Google tokens in the clear, which is defensible for the owner's own credentials and not defensible for a second business's. So `hostaway_connections.client_secret_encrypted` holds Fernet ciphertext, and the key lives in the environment (`HOSTAWAY_ENCRYPTION_KEY`), never in the database.
**The property this actually buys**: the secret is split across two places that are stolen by different means. Ciphertext without the key is noise; the key without a database read is noise. It defends against a **database-only** compromise — a leaked backup, a stolen dump, a service key in the wrong hands, a misconfigured RLS read.
**What it does not defend against, stated plainly so nobody mistakes it for more than it is**: anyone with code execution on the Render service has both halves, because the running app *must* have both to work. So does anyone with write access to the repo, via a deploy. And so does **the owner's own laptop** — `.env` holds the encryption key alongside Supabase credentials that bypass RLS, which is proven rather than assumed: `migrate_owner_hostaway.py` ran locally and wrote to the production database. The laptop is the richest target in the chain, richer than the database.
**Two accepted weaknesses**, both deliberate and both worth revisiting if this grows past one business: it is **one key for everyone** — the fifteen colleagues' secrets all encrypt under the same key, so it is a single point of compromise for the whole team, where per-user keys would be better and considerably more complex — and there is **no key-rotation path**. If the key ever leaks, the correct response is a new key plus re-encrypting every row, and no script does that today (see BACKLOG.md).
The key is read on every call rather than at import, so a deploy without it still boots and still serves every user who has no Hostaway connection. That promise was **broken in two places on the day this shipped** and is now held by tests — see CURRENT_TASK.md, Gap 0. The lesson generalises past crypto: introducing a raise into a path whose callers were written to fail soft is a change to those callers too, whether or not you touch them.

### Decision: dates are named by `Intl`, and the locale is read off `<html lang>`
(2026-08-25) Eight places formatted dates with a hardcoded `'en-US'`, so the calendar and the task cards stayed American whatever the user picked in Settings → Language. The obvious repair — seven weekday names and twelve month names per locale in `en.json`/`el.json`, which is what the rest of the UI does — was **rejected**, because assembling a date from named parts gets Greek wrong: the month is «Αύγουστος» standing alone in a heading and «25 Αυγούστου» next to a day. `Intl` already knows this per pattern; a lookup table would need the cases hand-maintained in two files and would drift the first time anyone added a format.
**Why the locale comes from `<html lang>` and not from i18n**: `utils/formatDate.js` is imported by the plain-node check scripts (`scripts/recurrence-badge.test.mjs` loads it for `isoWeekday`). Importing `i18n.js` to read `i18n.language` would pull react-i18next and React into a date utility and break that script for the sake of one string. `i18n.js` already writes the chosen language onto `<html lang>` on startup and on every switch — for screen readers — so the value is there for free, and `uiLocale()` falls back to `'en'` outside a browser, matching i18n's own fallback. Every component that renders a date already calls `useTranslation()`, so all of them re-render on a language switch and re-read it; that is what makes reading a global safe here, and it is the thing to re-check if a date ever appears in a component that does not.
**The detail that is not cosmetic**: `toUpperCase()` on a Greek weekday keeps the tonos — the browser's τρί/πέμ/σάβ come back as ΤΡΊ/ΠΈΜ/ΣΆΒ, and Greek does not accent capitals. `weekdayShortUpper()` strips the combining acute only, so dialytika survive (ΑΫΛΟΣ). It must be applied to uppercase output only; over lowercase text it would remove accents that belong there.

### Decision: a toggle is applied where the data is drawn, not by emptying the state behind it
(2026-08-25) `CalendarView`'s events effect cleared `calendarEvents` when the "show events" setting was off — the ESLint error that had been carried as a known baseline since 2026-08-07. Writing state from an effect body costs an extra render pass, and it was the wrong shape besides: the fetched events and the decision to show them are two different facts, and one was being used to erase the other. The toggle is now a one-line derivation at render (`visibleEvents`), and the effect only decides whether to fetch.
Two things fall out that the old version had to guard for separately: turning the toggle back on shows the cached week immediately while the refetch is in flight, and a late response can no longer repopulate the grid with the toggle off — which the long comment above the effect had been reasoning about at length, and which is now simply not expressible. That comment was rewritten rather than left; it described behaviour that no longer exists.
Generalises to the rest of this codebase: before adding an effect that sets state from other state, check whether the value can just be computed in the render.

### Decision: the category stops being a word and becomes a row (2026-09-01)
Design: `docs/superpowers/specs/2026-08-31-workspaces-and-categories-design.md`. Two levels the user creates and names — a **workspace** containing **categories** — replacing the fixed four words `Business/Personal/Unknown/Hostaway` that were locked in a CHECK constraint, Pydantic `Literal`s and the AI's own prompt.
The finding that shaped it: **only two of the four were categories at all.** Business and Personal are top-level areas — workspaces, in the owner's own example. `Hostaway` is a **provenance**, written by the webhook and never by a human. `Unknown` means "the classifier could not tell". That reframing turned the migration of 301 live tasks from a guess into an obvious mapping.

### Decision: the task points at a category by ID, not by name
The cheaper option — drop the CHECK and let the TEXT column hold any word — was considered and rejected. Renaming is not hypothetical: a user who creates `γραφείο` will rename it, and with names-as-text every task created before that silently keeps the old word. The failure is invisible when it happens and undiscoverable afterwards. An id makes rename free and delete recoverable.

### Decision: deleting a container never deletes work
`tasks.workspace_id` and `tasks.category_id` are both ON DELETE SET NULL. Delete a category and its tasks become unfiled; delete a workspace and its categories cascade away but its tasks survive. The user must never lose work as a side effect of tidying up.

### Decision: the workspace switcher filters what you LOOK AT, never what the system DOES
Reminders, calendar sync, the daily summary, the Hostaway webhook and escalation all ignore it. A reminder the user set must ring whatever they happen to be looking at; anything else means the app silently loses an alarm. This is a safety property, not a preference, and it is written down so a later "make it consistent" refactor does not quietly break it.

### Decision: two AIs, treated oppositely, because they do opposite jobs (2026-09-02)
The **extractor** classifies ONE new thing, so it is scoped to ONE workspace and shown only that workspace's category names. The **agent** answers "what do I have", so it still sees every task and only its vocabulary changes. Measured before building: a model asked to pick a workspace from all of them scored 7/7 across 24 calls with every answer stable — so on "Όλα", where nobody knows the workspace, the extractor is now asked for it too. Standing inside a workspace it is never asked, and returns nothing for the field.
The owner's framing drove this: *"δεν χρειάζεται να μπερδεύεται — να βλέπει μόνο τις κατηγορίες του χώρου που είναι"*.

### Decision: the model answers with a NAME; Python resolves the name to an id
Models truncate UUIDs, transpose them and invent plausible-looking ones. Every AI path — the extractor, the per-task editor — returns a name, and `services.resolve_category_name` / `resolve_workspace_name` look it up **inside the workspace that won**. An unrecognised name resolves to nothing and the task is left unfiled. **No workspace or category is ever created from model output**: a hallucinated container looks deliberate, which makes it worse than none.

### Decision: the agent's vocabulary is APPENDED to its system instruction, never interpolated into it
`agent_tools.build_system_instruction` is a constant on purpose — its docstring records that interpolating the clock made the ~2,900-token prefix change every minute, so caching never engaged (0.4% over 136 runs) while that block was **74% of every prompt token ever billed**. A category list is not a clock; it changes weekly, so it stays stable across one user's consecutive requests. It goes at the END regardless, so the long static block above it remains a shared prefix, and a test asserts the static instruction is still a prefix of the dynamic one. A user with no workspaces gets `""` and therefore the byte-identical old constant.

### Decision: the per-task editor changes categories, never workspaces (2026-09-02)
`workspace_id` is absent from `TASK_AGENT_WRITABLE_FIELDS` — not merely unvalidated, but not writable, so there is nothing for the model to aim at. The owner drew the line: changing a category is a small move inside the box you are looking at, while changing the workspace takes the task off the screen you are standing on. Ask for "move it to Friday", have it also decide the task is Personal, and the task vanishes in front of you.
The old four-word `category` field was removed from that editor's schema at the same time. Measured: with it present, "put it in crypto" also set `category='Unknown'` (an edit nobody asked for, shown in the change list) and "move it to Personal" set `category='Personal'` and reported **done** when nothing visible had moved. A phantom change is bad; a false confirmation is worse.

### Decision: a bare hour is a question of meaning, not arithmetic (2026-09-02)
The extractor's instruction gave the model today's DATE and no clock, so "ραντεβού στις 7" said at 20:38 produced 19:00 today, 07:00 tomorrow and 19:00 tomorrow across three consecutive attempts. Adding the time alone was not enough — measured 4 more times, it still answered 19:00 today twice. The rule that works asks what the person MEANT: a meeting at 7 is 19:00, a wake-up at 7 is 07:00, and the day follows from whichever hour that is. 15 calls, every one stable, no past time in any run.
Recorded because the owner asked whether the explicit rule was wasted words. It was measurement, not opinion, that answered him — and the first, mechanical version of the rule ("the next time that clock reading happens") was literally correct and humanly wrong.

### Decision: every account starts with Business AND Personal; integrations land in Business (2026-09-03)
The owner is aiming this at companies: a company uses both halves and a sole trader can ignore one. `services.ensure_account_workspaces` furnishes them lazily on the first workspace read, with Business as `default_workspace_id`. No categories are seeded — the workspaces are structure, the categories would be a guess about someone's life.
This also retires a real limitation rather than solving it: a category **cannot be moved between workspaces**, so an integration's category created in whatever single workspace happened to exist would be stuck there. Business always existing removes the question. Moving a category between workspaces is parked (see BACKLOG.md) because there is no obviously right answer for the tasks already filed under it.

### Decision: the extraction instruction says WHEN a checklist is built, not just what shape it takes (2026-09-03)
The instruction described a checklist item's shape (`{text, done}`) and never said when to build one. The shape is already enforced by `response_schema=TaskList`, so those words bought nothing; the decision the model actually had to make was unguided, and it made it differently on identical input. "να πάω το παιδί στον γιατρό και μετά στο σχολείο" came back once as one task that had **silently dropped the school**, and once as one task with two items. The owner's complaint was over-splitting; the measurement showed the real fault was instability in both directions.

`ai_engine.py`'s `_build_system_instruction` now carries the rule instead: one piece of work the user names **together with its parts** becomes one task with an item per part; two things they simply want done stay two tasks, same day or same outing notwithstanding. Two examples anchor the shapes.

**Do not shrink this line.** Three cheaper wordings were measured against the real model and all fail the same way — they merge what should stay separate, because a loose trigger ("same job with sub-steps") is permission to merge with no reason to split, and the model always finds something shared ("this afternoon", "tomorrow"):

| wording | chars | score |
|---|---|---|
| shape only (what shipped before) | 192 | 11/15, and unstable run-to-run |
| "same place, same trip, same sitting" | 195 | 8/11 |
| "same job with sub-steps" alone | 115 | **0/4** |
| that + the two-things brake, no examples | 176 | 5/8 |
| **narrow trigger + brake + 2 examples (shipped)** | **273** | **8/8, and 14/15 across the wider set** |

82 real calls over five rounds. Cost: +81 characters on a 1,573-character instruction (+5%), which also buys the removal of a redundant JSON example. One builder feeds all three capture paths (text, audio, image), so this is one line for all of them.

**Known soft spot:** "doctor then school" is genuinely one outing with two stops and lands correctly in 2 runs out of 3. Left alone deliberately — another sentence in the prompt is not worth 1 case in 15.

### Decision: deleting a task stamps `deleted_at` instead of removing the row
2026-09-04, owner's decision. `repository.delete_task` ran a real `DELETE` until this date; it is now `repository.soft_delete_task` (renamed so a missed call site raises instead of silently keeping the old behaviour), with `repository.restore_task` to undo it and `POST /tasks/{id}/restore` in front of that. The row survives because the rows **are** the archive Browse's History tab reads.

**This reverses a decision that was previously explicit.** `test_deleting_an_ordinary_task_still_hard_deletes` asserted the opposite and gave its reason: *"turning every delete into a soft delete would mean the app never frees a row."* Freeing the row is exactly what was given up, deliberately — it destroyed the only answer to "what did I have last month" and to "I deleted that by mistake", which was worth more than the space. The test now asserts the new behaviour and records what it used to say.

Not a `task_history` table: `created_at` and `completed_at` are already on the task row, and a second table would mean keeping two records of one life in step. Not a reuse of `cancelled_at` either — that column exists for a mechanical reason (the generator recreates a hard-deleted `occurrence_date` within ~2 minutes) that does not apply to an ordinary task. `services.delete_task` routes on `recurrence_rule_id`; both stamps read as "Διαγράφηκε" in the UI and `restore_task` clears both at once. Enforced in exactly two places — `agent_tools.is_open_task` and `taskDisplay.isVisibleTask` — which is what keeps a deleted task out of the agent, the reminders, the escalation query and every screen simultaneously. See DATABASE_SCHEMA.md.

**`repository.delete_tasks_by_ids` still hard-deletes, on purpose.** Its two callers are recurrence housekeeping, not a user deleting work: editing a rule drops the future occurrences the user never touched so they can be regenerated on the new schedule, and deleting a rule drops its open occurrences because with no rule there is no `grace_days` left to close them by. Those rows are regenerable placeholders nobody chose to remove. Soft-deleting them would fill the History tab with dozens of "deleted" entries for an act the user never performed, which makes the feature worse rather than more complete. If a "deleted by the system" bucket is ever wanted, that is the decision to reopen.

### Decision: restore has no time limit, and does NOT bring back the Google Calendar event
2026-09-04, both halves the owner's call, both deliberately asymmetric with what a "trash bin" usually implies.

**No cutoff.** Nothing purges deleted rows, so a 30-day limit would be code whose only job is to refuse something that works. If a purge is ever added, this decision is what has to be revisited first.

**The calendar hole is accepted, not overlooked.** Deleting a `calendar_origin='app'` task removes its Google Calendar event immediately, and Google is outside this database — there is no undo to reach for, and recreating the event would mean a new event id, fresh invites, and a second entry in anyone else's copy of the calendar. So `services.restore_task` clears the dead `google_event_id` and returns `link_cleared`, and the UI must say so rather than reporting a bare success: a task pointing at an event that no longer exists is worse than an honest one with no link, because the sync would keep trying to update a ghost. Asserted by `test_restoring_an_app_origin_task_clears_the_dead_calendar_link` so it cannot be quietly closed or quietly forgotten. A `calendar_origin='google'` task keeps its link — that event was never deleted.

### Decision: the calendar button pushes NOW, and the pull writes only on a real change
2026-09-04, both halves forced by the same measurement, not by reading the code.

**Pressing the per-task calendar switch sends the task immediately.** The owner reported the button as broken: nothing reached Google, then turning the global "sync all" on made the task appear, then the button "started working". The investigation found **no asymmetry between the two switches** — they feed the same queue, filtered by the same rule, drained by the same ~2-minute tick. There was never a lock for sync-all to open; what differed was the two minutes. So the fix is not in the queue, it is in the wait: `services.push_task_to_calendar_now` runs inside the PATCH that sets the flag, with the same eligibility rules the queue uses, a 5 s timeout, and a guarantee that it never raises and never blocks the save. On failure the flag is still stored and the next tick retries — i.e. exactly today's behaviour, which is why this can only be faster, never less reliable. `main.py`'s `create_recurrence` had already made this call for the same reason and says so in its docstring; the calendar simply never got the same treatment.

**The pull no longer rewrites a task that has not changed.** Proving the first half meant measuring the live database, and the measurement found something bigger: sampled 170 seconds apart with nobody touching the app, **105 of 109 task rows had a fresh `google_last_synced_at`** — the pull was writing every linked event back unconditionally, ~75.000 identical writes a day. The waste was the smaller half. `get_tasks_needing_calendar_push` decides what to send by comparing `updated_at` against `google_last_synced_at`, so a stamp written by the pull can land AFTER a genuine edit and hide that edit from the push queue permanently. This is the 2026-08-28 `updated_at` bug seen from the other side: there the push kept re-sending because the stamp moved forward, here the pull kept re-stamping and could stop a send altogether.

**Why one batched read and not a read per event.** Checking each task before writing it would have traded ~105 writes for ~105 reads per tick — the same number of round trips, no faster. `repository.get_tasks_sync_snapshot(user_id, task_ids)` fetches the whole page's tasks in one query. It is scoped by `user_id` although the ids arrive from Google, because they come out of an event's extended properties: an id that does not resolve to one of this user's tasks is simply absent from the result and nothing is written for it, where the old code would have issued a blind unscoped UPDATE by id.

**What was deliberately NOT done here.** Turning the switch OFF still leaves the Google event in place; deleting it is decided and specified but is its own delivery (see BACKLOG). Timeouts were added only to the two calls that can now run inside a user's request — the token refresh and the event push — not to the pull, whose behaviour on the scheduler's own path is unchanged.

**The same fix next door, on the owner's own events (added the same day).** Proving the two changes above on the live system produced the number that found the next one: in the 170-second window where task rows were rewritten `0` times, `google_calendar_events` rows were rewritten **46 of 64** — the owner's own appointments, re-stored every tick with identical values, ~33.000 writes a day. That count was doing double duty as the proof that the scheduler tick was still running at all (it is an untouched code path, so a moving stamp there means the tick ran), which is why "task rows stopped changing" could be read as a fix rather than as a dead cron. The foreign-event upsert now compares first, through `get_google_calendar_events_snapshot`. It is the milder version of the bug — nothing in this table feeds the push queue, so no edit of the user's can be hidden by it — and it was fixed only after the owner asked for it, not folded silently into the delivery he had approved.

**SEEN WORKING — 2026-09-04, against the live account, and how.** All times UTC. The immediate push: the owner pressed a task's calendar button at `19:29:12`, and the event id was stored at `19:29:13` — **+0,7 s**, where the same press used to wait up to 120. The pull: task rows rewritten in a 170-second window went from **105 of 109 to 0 of 110**, and `google_calendar_events` rows from **46 of 64 to 0 of 64** — about 108.000 writes a day that stopped.

Then the half that actually matters, and the reason those zeros are not enough on their own: **an empty queue and a dead sync produce the identical number**. So, exactly as the 2026-08-28 migration file insists ("step 3 is the one to insist on"), one real change was made on Google's side — one event moved at `20:12:23` — and the app was watched to see what it did with it: **exactly one row updated, at `20:14:14`, with the other 109 untouched**, the new time landing in the task itself. One tick, one change, one write. That is both halves: the writing stopped, and the syncing did not.

**Not proven live, and worth saying so:** that a FOREIGN event (one of the owner's own appointments rather than an app-created one) is re-stored when it genuinely changes. Live evidence covers only that unchanged ones are left alone; the write-on-change path for that table rests on its unit tests. Closing it needs nothing more than changing the time on a personal appointment and looking.

### Decision: every screen refreshes itself — on return to the app, and once a minute while open
2026-09-05. Reported as a calendar bug and it was not one.

**The symptom.** The owner created an event in Google Calendar, it did not appear in the app, and it appeared only when he turned the "show Google events" switch off and back on. His own words: «περνάει μόνο άμα κλείσω και μετά ξανά ανοίξω το κουμπί».

**The sync was innocent, and this was measured before anything was changed.** The event (`Κλασε`) was created on Google at `07:02:18` UTC and was in `google_calendar_events` at `07:04:13` — **1 m 55 s**. Asked directly, Google confirmed it was the only genuinely foreign event of those days; everything else in that window carried our own task-id marker, i.e. the app had put it there. `PATCH /settings` was read to the bottom for the same reason: `calendar_show_events` is a stored boolean and **nothing else** — no Google call, no sync-token reset — so flipping it could not possibly have fetched anything from Google.

**The real hole: nothing ever asked twice.** `TodayView` fetched its events when the day or the toggle changed, `CalendarView` when the visible range or the toggle changed, `App` loaded tasks when a session appeared. There was no timer and no return-to-foreground handler anywhere in `frontend/src` — the only `setInterval` in the codebase belonged to the voice recorder. So while the app sat open, the screen was a photograph of whatever the server held at launch, and **flipping that switch was the only control on the screen capable of forcing a fetch**. This is the second time a wait has been mistaken for a broken button (the first is the entry above, 2026-09-04, in the opposite direction) — and this time the button really did cure it, for a reason that had nothing to do with what the button is for.

**Tasks had the identical hole and were fixed in the same pass**, at the owner's instruction: a Hostaway message, an occurrence generated at midnight, or an edit made on the other device were all invisible until a reload.

**`useAutoRefresh(refresh)`**, one hook, three callers. Two rules in it are not decoration:
- **Nothing fires while the screen is hidden.** A phone in a pocket must not spend requests, and the return-to-foreground refresh already covers everything missed while it was away.
- **The timer calls the NEWEST refresh function, never the one it was created with.** These callbacks close over what is on screen; a timer holding the original would quietly put September's events back on an October screen. Hence the ref. `CalendarView`'s per-request id exists for the neighbouring race: the background refresh and a month change now issue overlapping requests, so newest-answer-wins has to hold across both callers, where the old `cancelled` flag only ever protected its own effect.

**One minute, deliberately shorter than the server's ~2-minute pull**, because the two waits add up: 2 + 2 would have made a new calendar event take up to four minutes to appear.

**A background failure only reaches the console.** `refreshTasks` toasts because a person asked for that fetch; nobody asks for these, so a phone losing signal in a lift must not raise an error the user can neither explain nor act on.

**Deliberately not done.** No websocket, no push-driven invalidation, no refresh on scroll or on tap. And the Today screen still asks only for events that START today — the reported event began at 23:30 the previous night, so it would never have appeared there whatever the refresh did. Whether an event that began yesterday belongs on today's screen is a product question, not a bug, and it is not answered here.

**Unseen, and it is the whole point of the change:** an event created on Google appearing on the owner's phone **without him touching anything**. Tests, lint and build prove the code is sound (`auto-refresh.test.mjs`, 7 checks, both broken models kept alongside so the scenarios are known to discriminate); they cannot prove a screen refreshed itself. That needs him, the app open on the Calendar, and about two minutes.

### Decision: a desktop shell at 1024px — a left sidebar instead of the bottom tabs
2026-09-05. Asked for in the owner's own words: «θελω να φτιαξουμε ενα ξεχωριστό ui στον υπολογιστή… αντι να ειναι κάτω σε pills να ειναι αριστερα όπως τα dashboards… να μην αλλάξει όμως τίποτα απο την λειτουργεία και μονο για pc και tablets».

**Not a second app, and that was the first thing settled.** One codebase, one set of views, a different shell above a width. Two apps would mean every future change made twice, and the four screens do not need to know which shell they are inside — `InboxView`, `TodayView`, `CalendarView` and `BrowseView` were not edited at all in this pass.

**1024px, chosen by the owner** from three offered widths, and deliberately equal to Tailwind's own `lg`. Below it — a tablet held upright — a 256px column would take a quarter of the screen from the list, so that case keeps the phone's bottom nav. `DESKTOP_QUERY` in `hooks/useMediaQuery.js` and every `lg:` class in the app are therefore the same number by construction, not by coincidence.

**A JavaScript branch, not `hidden lg:flex`.** This is the one non-obvious engineering choice. CSS would be the smaller diff, but the two navigations are not two skins of one thing: the desktop one owns the add-task control, and `FloatingActionButtons` mounts a microphone and two file inputs. Rendering both trees and hiding one would mount that machinery twice on every screen at every width. `useMediaQuery` is built on `useSyncExternalStore` rather than `useState` + `useEffect` — the first version re-read the query inside an effect to close the gap between first render and the listener attaching (a tablet rotated in that window would be missed), and that re-read is a setState-in-effect, which React 19 flags and which took project ESLint from 12 to 13.

**What the sidebar carries, decided by looking at what this class of app actually does** rather than by taste: the add-task button at the top, the four tabs, then the workspaces, then the account at the foot. Todoist's sidebar is add-button → fixed views → *projects*; the owner's workspaces ARE that list, which is why they left the chip row (`WorkspaceBar`, ~40px off every screen) and moved into the column. The agent deliberately stayed in the top bar: it is an action, not a location, and it is this app's distinguishing feature — burying it in a list of places would be a demotion.

**The reading width did not change; Calendar alone widened.** The 45–75-characters-per-line rule lands at 680–780px, and this app's existing `max-w-3xl` is 768 — already correct, so lists were left exactly as they are. A month grid is a table, not prose, and the same cap only shrinks its day cells, so `CalendarView` takes `lg:max-w-none` and `AppBar` takes a matching `wide` prop so the title stays over its own content instead of floating in the middle of the grid.

**One structural change fell out of it.** The four tab icons and the `TABS` array lived inside `BottomNav.jsx`. Both navigations need them, and a module that exports a component may export nothing else without tripping react-refresh, so the icons went to `icons.jsx` and the list to a new `components/navTabs.js`. `scripts/ui-check.mjs` parsed `BottomNav.jsx` for that array and now parses `navTabs.js` — its four-tab / twelve-character budget is still the BOTTOM nav's (the sidebar has room to spare), but both navigations read the one list, so checking it there still covers the case that can clip.

**Seen, and it counts:** the owner ran it locally, logged in, and reported it working. The backend log for that session is the corroboration — 297 tasks and calendar events served, `GET /workspaces`, `GET /recurrences`, `GET /settings`, a weekly-range `GET /calendar/events` (so he reached Calendar and changed its mode) and a `PATCH /settings` (so he used the sidebar's workspace switcher and it wrote through), **zero 4xx or 5xx across the whole session**.

**Not seen:** the add-task dropdown in its sidebar shape — dictation and photo from a desktop have never been exercised. And no screenshot of either layout exists: the browser tab available to the assistant does not share the owner's session, so the visual record is his eyes, not a captured image.

### Decision: an add lands in the Inbox, and the new task keeps its mark until it is found
2026-09-05. Two owner requests hours apart, which turned out to be one behaviour.

**Why the Inbox, and not "stay where you are".** Everything the + produces — typed, dictated, photographed — is saved with no `approval_status`, i.e. waiting to be approved, and `InboxView` is the only screen in the app that lists those (`!task.approval_status`, the same filter the tab badge counts). Added from Calendar or Today, the task therefore existed and was invisible: a success toast, a number on a badge, and nothing on screen. The switch goes through `handleTabChange` rather than `setActiveTab`, so an add closes an open row exactly as a manual tab tap does — one behaviour, not two that can drift apart.

**All three add methods, by the owner's decision** («ναι απο ολα οχι μονο απο το κειμενο»). They already funnel into one handler, `handleTasksAdded`, so this is one line rather than three, and the desktop sidebar's "Νέα εργασία" button inherits it without being touched — it is the same component in a different shape.

**Why the mark persists instead of expiring on its own.** Offered as a straight choice: three pulses and gone, or three pulses and the ring stays. He took the second, and it is the right one for what he actually reported — «μεχρι να διαβασω ποιο ειναι χανω λίγο χρόνο». A mark that fades on a three-second timer does not answer "how long does it take to find it", it races it. It comes off when the row is opened, because opening it is the proof it was found, and only off that row — one extraction can return several tasks, and clearing them all would punish reading the first. The twelve-second timer is the fallback for a task nobody touches, and a second add restarts it rather than letting the older timer cut the newer mark short.

**Amber, and the reason is not taste.** It is already this app's "pending approval" colour (`--priority-p2`, the same amber as the «εκκρεμεί» label inside the card), and everything the + makes IS pending — so one signal carries both facts instead of two competing ones. Red is taken by destructive actions and blue by the open row; either would have said something it does not mean. Two new tokens (`--highlight-new`, `--highlight-new-glow`) rather than borrowing the priority ones, because a colour named for what it MEANS survives someone re-tuning priority colours later. `ui-check` rule 5 then forces both into the dark palette as well (47 → 49 tokens).

**The mark is on the wrapper, not on the card, and that is the one non-obvious mechanical choice.** `TaskRow` renders a wrapper with `overflow-hidden` — the thing that hides the swipe tray until you drag — and overflow clips CHILDREN, so a halo drawn on the card inside would be cut off at exactly the edge it has to cross. An element's own `box-shadow` is not clipped by its own overflow, so the class goes on the wrapper and works. `z-index: 1` in that class is the same problem from the other side: the next card's background is opaque and paints after, so without it the halo is clipped along the bottom edge only, which reads as a rendering bug rather than as a design.

**Reduced motion keeps the information.** The steady ring is the class's own `box-shadow` and the animation only adds the expanding halo on top of it — so `@media (prefers-reduced-motion: reduce) { animation: none }` removes the movement and leaves the mark. This is deliberately not the blanket `animation: none` the two older animations in that file take: for those, nothing is lost when the motion goes; here it would delete the whole feature for exactly the people that setting exists for.

**The ring pulses, not just the halo — corrected hours after shipping.** The first version held the ring at a constant 2px and animated only a soft halo outside it, expanding and fading. That passes for a pulse on a preview page and does not on a phone: the owner's report was «δεν αναβοσβηνει», and he was right — nothing about the mark ever changed, a faint wash simply moved outward from a static edge. The ring now goes 2px → 5px → back on each of the three beats, with the halo thrown out on the same beat. Worth keeping because it is the general lesson, not the specific one: an animation whose only moving part is a low-alpha shadow outside a constant shape reads as a still image on a bright screen at arm's length. **What was NOT changed in the correction:** the possibility that his phone reports `prefers-reduced-motion: reduce` — Android and iOS both have the accessibility toggle, and battery saver turns animations off system-wide on both — in which case the pulse is suppressed on purpose and the static ring is all there ever was to see. That is a setting to read on the device, not a defect, and the honest fix there would be a stronger STATIC mark.

**What proves this, and what does not.** `npm run check` exit 0 (206 checks, `ui-check` confirming both palettes carry the new tokens), lint at its unchanged 12-problem baseline, `vite build` clean, and the class, keyframes, both palettes and the reduced-motion rule grepped back out of the built CSS so the Tailwind pipeline is known not to have dropped them. The animation was then watched in a browser, on a throwaway page carrying the real keyframes and real token values, at three strengths in both themes — which is how the owner chose the middle one. **None of that is the app.** The full path — a real add, the tab switching, a real card wearing the ring — has deliberately not been run, because every add through the + is a paid Gemini extraction on the owner's own account. Also unobserved: where the Inbox is scrolled when you arrive on it, since switching tabs does not reset the page scroll.
