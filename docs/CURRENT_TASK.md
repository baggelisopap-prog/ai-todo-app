## Gap 2 — `relaxed_matches` has never fired in a live run
When a multi-filter `search_tasks` returns 0, `over_filtered_hint` now also returns `relaxed_matches`: the rows the same search finds with filters relaxed, so "you have none" cannot be reported over a self-narrowed result. ## Gap 3 — an English question is answered in Greek
Reproduced twice ("What do I have today?" → Greek answer), in both the before and after suites, so it is stable and not a fluke. Untouched so far.
**The stated cause was wrong, and the candidate fix should NOT be tried.** This file previously blamed the rule sitting in the LAST line of a ~7.800-character instruction and proposed moving it up next to the agent's identity. The per-task agent (2026-08-07) refutes that: its instruction is a twentieth the size, the rule was in its FIRST line, and it still answered English instructions in Greek — 2/2. Strengthening the wording flipped every Greek answer to English instead, also 2/2. The model follows the language of the DATA (every task in this app is Greek), not the question, and no placement or phrasing was found that holds both directions.
**Fix to apply**: the one that worked there — decide it in code and state it as a fact. `task_agent.answer_language()` checks the instruction for Greek script and the prompt says "Write "message" in Greek."/"in English."; 22/22 correct both ways afterwards. The chat agent's equivalent would set the language from `question` (after `strip_test_label`) and inject the same line into the current user turn. See DECISIONS.md.

## Still open from before this overhaul (unchanged)
- **Day view + conversation memory were never verified through the real logged-in UI.** The mechanisms are confirmed working in-process, but the original `#dv1`..`#dv13` and `#m1`..`#m8` checklists (two-account isolation, stale-state, refs-over-5, prompt injection, modal lifecycle) were never run logged in. The checklists are preserved in PROJECT_STATUS.md.
- **`get_tasks_for_user` loads every task ever, and it is the agent's biggest non-model cost.** Measured 2026-08-07 on the owner account: **124 rows fetched in ~930 ms to use 5 open ones**. Not a token cost (filtering happens in Python) but ~1 s of latency on EVERY agent request before the model is even called. The fix is to filter in the query (`is_rejected=false`, `approval_status=true`, and completed only when asked) so ~5-20 rows come back instead of 124; deliberately not done as part of the agent overhaul because `repository.get_tasks_for_user` is called from well outside the agent path and changing what it returns needs its own pass.
  A related note, **corrected**: an earlier version of this file said `search_tasks` scanning the list "up to three times" had made this more pressing. Benchmarked: the scan count is actually up to ~9 in the worst case (main scan, completed retry, nearby-dates lookup, and one pass per filter relaxation), but the cost is negligible at real sizes — **3 ms simple / 9 ms worst case at 124 tasks**, i.e. roughly 1/100th of the fetch it follows. It only becomes comparable to the fetch at ~10.000 tasks (245 ms / 738 ms) and painful at 50.000 (1,2 s / 3,6 s). The scanning is not the problem; the fetching is.
- **Retry accounting gap**: if an attempt fails *after* the model generated, Google billed but `token_usage_log` never counted it. No overall request timeout either (backoff up to 3s/round × 4 rounds). Related, found 2026-08-07: `agent_engine._SummedUsage` has no `thoughts_token_count` attribute, so `token_tracker.log_token_usage` reads it as 0 and `calculate_cost` — which bills thinking at the output rate — **understates cost whenever the model thinks**. Harmless today (flash-lite reports 0 thinking tokens; verified prompt + output = total exactly across 136 runs) and a landmine the day the agent model changes. The `max_rounds_recovered` path separately fails to accumulate thinking/cached at all.
- **The contamination guard's cheaper variant is unverified.** `propose_update_task` currently *errors* on a field value copied from another task, which costs the model 2 extra rounds to recover from (2 → 4, landing exactly on `MAX_TOOL_ROUNDS`). Dropping the offending field with a note instead — exactly how no-op fields are already handled — should get the same result in 2 rounds. Narrow blast radius either way (7 blocks in 282 runs), but it is the one loose end from that pass.
- **The 26-case suite has not been re-run since the contamination guard landed.** Only the follow-up pair was re-verified (5×). The guard lives inside `propose_update_task`, so `prop_update` ("άλλαξε την ημερομηνία της παρουσίασης στρατηγικής") is the one other case that could be affected; it ran 3 rounds and was never blocked in 5 pre-guard runs, but that is not the same as testing it after.
- **`no_matches_hint` only fires when a date filter is present** — a keyword-only search that finds nothing gets no hint. Partly mitigated now (`over_filtered_hint` covers multi-filter cases, and the word/stem fallbacks mean a keyword miss is more likely to be genuine), but the gap itself is unchanged.
