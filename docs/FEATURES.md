# FEATURES — how each feature works and its scope boundaries
_Each section self-anchors. "Scope" lines state what is deliberately OUT of scope._

### Feature: Task capture & extraction — text/voice/image via Gemini
`ai_engine.py` extracts structured task data (name, description, suggested category/priority, due date/time, checklist) from text, voice, or image input. Suggestions are `ai_suggested_category`/`ai_suggested_priority`; the user approves/rejects. Priorities: P1/P2/P3.
**Splitting vs. checklisting (2026-09-03)**: one piece of work the user names together with its parts ("3 bugs in the app by Friday") becomes ONE task with an item per part; two things they simply want done stay two tasks, even on the same day or the same outing. Before this the instruction only described a checklist item's *shape* and left the decision unguided, so identical input produced different splits between runs — and in one it dropped half the input. Measured, 8/8 on the discriminating cases; three shorter wordings were tried and all merge too eagerly. See DECISIONS.md before shortening that line.
**CORRECTED 2026-09-03** — this line used to read "Categories: Business/Personal/Unknown/Hostaway". Those four fixed words are gone from every screen. Categories are now rows the user creates inside a workspace they name, and the extractor is handed **that workspace's names only** — it answers with a name and Python resolves it to `tasks.category_id`, filing nothing if the name is unrecognised. `tasks.category` still exists in the database and is still written; nothing user-facing reads it. See DECISIONS.md, "the category stops being a word and becomes a row".

### Feature: Notifications — reminders, daily summary, per-user push
Runs inside `run_notification_scheduler()` (per-user loop, every ~2 min via external cron). Sends per-task reminders and an optional daily summary. Push is per-user via `send_push_to_user(user_id, ...)` (Web Push / VAPID). Scope: `send_all` and daily-summary settings live in app_settings; a notification only fires to the correct user's own devices (a prior `send_push_to_all` was replaced to prevent cross-user notification leakage).

### Feature: Hostaway integration — guest messages become tasks (per-user since 2026-08-14)
Webhook receives Hostaway guest messages; Gemini classifies them; qualifying ones become tasks in the locked **Hostaway category** with escalation reminders (e.g. 30'/1h/2h). **Since 2026-09-01 escalation matches that category's `system_key`, not the literal word** — `repository.get_active_hostaway_tasks` looks up the one category row carrying `system_key='hostaway'`, which is what let categories become user-defined without the integration noticing. Since 2026-09-03 that category is created when the user CONNECTS Hostaway, not for everyone. Guest-message text is treated as DATA, never instructions (see agent injection defense).

**Any user can now connect their own Hostaway account**, from Settings → Hostaway. The "one door" `get_user_id_for_hostaway_account()`, hardcoded to the owner, is gone. Design: `docs/superpowers/specs/2026-08-13-hostaway-per-user-integration-design.md`. Plan: `docs/superpowers/plans/2026-08-13-hostaway-per-user-integration.md`.
- **The Settings screen** takes an Account ID and an API key, checks them against Hostaway *before* storing anything (a saved-but-broken connection fails silently later, on a guest message nobody is watching), registers the webhook on the user's account, and stores the secret encrypted. The key field is write-only in both directions: `type=password` going in, and the status endpoint never returns it coming out. If the webhook could not be registered, the screen shows the URL to paste into Hostaway by hand instead of claiming the connection is complete. Disconnecting removes the webhook, then the row — and still removes the row if Hostaway refuses, so a webhook we cannot delete never traps the user. **Existing Hostaway tasks survive a disconnect**: they are the user's work, not the connection's data.
- **Two switches**, both on by default. *Create tasks from messages* — a new guest message becomes a task. *Close the task when you reply* — replying to a guest closes the task it belongs to, within about two minutes (the scheduler tick). Each is checked before any work is done, so "off" costs nothing: no Gemini call, no Hostaway HTTP call.
- **One account, many colleagues.** Fifteen staff share the owner's Hostaway account, and a guest message arrives once, carrying only `accountId`. It becomes **one task per connected colleague**, from **one** classification and **one** pair of enrichment calls — N colleagues do not mean N Gemini calls. Whoever answers, every copy closes on its own, because each colleague's reply poll sees the same reply. This is why `account_id` is deliberately not unique in the database.

**Message threading, the conversation link, and auto-complete on reply (2026-08-10).** Implemented, unit-tested, NOT yet exercised against a real webhook delivery. Design: `docs/superpowers/specs/2026-08-10-hostaway-threading-design.md`. A Hostaway task no longer means "a message arrived" — it means **"this conversation is waiting for me"**, and all three behaviours fall out of that.
- **Threading**: an incoming message within **90 seconds** of the previous one in the SAME conversation is appended to that task instead of creating a second one, so «καλησπέρα σας» / «είμαι ο Κώστας» / «δεν βρίσκω τα κλειδιά» is one task rather than three. The window is measured, not chosen: across 141 real consecutive guest-message pairs every burst was under 42 s, nothing fell between 1 and 2 minutes, and the earliest genuinely-separate second problem was 2.4 minutes out («den exv mpataria» → «δεν εχω νερο»), which must stay two tasks. Comparison uses **Hostaway's own `date`**, never `now()`, so it is unaffected by how or when the message reached us. Every failure path (unparseable date, missing previous message, out-of-order delivery) starts a NEW task — the safe direction; nothing is ever dropped.
- **The whole thread is re-classified on each append**, not just the new message, because the merged messages are exactly the ones that mean nothing alone («του νησιού», «Πετσέτες εννοώ συγγνώμη»). Call count is unchanged at one per message; the thread costs ~23 extra tokens across a burst against a 341-token fixed instruction. Priority can only escalate (`higher_priority`), and a burst re-notifies **only on an escalation** (`is_more_urgent`) — three pushes in forty seconds for one thought is the noise the feature exists to remove. Note the task NAME does not change (it is `Hostaway: {guest} - {listing}`, which carries no summary); what changes is the priority, the description's summary, and the message count.
- **The link**: the expanded task sheet links to `dashboard.hostaway.com/messages/inbox/{hostaway_conversation_id}`, confirmed against a real inbox URL rather than documentation.
- **Auto-complete on reply**: a human reply completes a **P3** task, and only P3 — `HOSTAWAY_REPLY_AUTOCOMPLETE_PRIORITIES` in `services.py`, the least urgent priority alone, staged that way on 2026-08-13 («για αρχή, μην χάσω κανένα τασκ») and deliberately kept there when the owner reviewed it on 2026-08-23. This line claimed "P2/P3" for ten days while the code said P3; it was wrong from the day the set was introduced. Every other priority records `hostaway_answered_at`, which stops the escalation nagging but leaves the task on the list to be closed by hand — including **P1**, where "I'm coming in 20 minutes" is an answer, not a fixed problem. Two open tasks for one conversation are left untouched and reported by push, since one reply cannot be attributed to one of them.
- **How often the two gates actually bite, measured over the first ten days** (2026-08-13 → 08-23, 39 Hostaway tasks; read out of `tasks` and the live conversations API, not inferred). **Detection is exact**: every human reply that landed while its task was still open was recorded, and each task without a `hostaway_answered_at` either never received a human reply or had been closed by hand *before* the reply arrived — 119 minutes before in one case, 47 hours in another. Zero misses. **Completion is the narrow part**: 8 of the 27 detected replies closed their task. Of the 19 that did not, **11 were blocked by the ambiguity rule and 6 by P3-only staging** (2 more predate the poller's deploy). The ambiguity rule compounds, and that is the part worth knowing: nothing closes what it blocks, so the open tasks in a conversation accumulate — 47691626 and 45902159 each reached **7** — and past two, no reply in that conversation can ever auto-close anything again. This is why the feature can look like it "stopped working" while every decision in it is behaving as designed.
- **The signal is `userId`, and this is the sharpest part.** The account runs a `messageReceived` automation ("we received your message and will reply shortly") that fires after EVERY guest message, so the obvious implementation — an outgoing message means the task is handled — would have closed every task within seconds of creating it, silently. Across 25 conversations: 66 Hostaway automations, `userId` null on all of them; 24 outgoing messages without a `communicationId`, 23 carrying `userId`. The one that disagreed is a **GuestArrive** third-party message with NEITHER field set, which is why `communicationId` was rejected as the signal. Known limit, failing safe: a reply sent from the Airbnb/Booking app may carry no `userId`, in which case the task just stays open.

### Feature: Recurring tasks — Slice 1, the mechanism and the form (2026-08-17)
A rule — weekly on a chosen set of weekdays, or monthly on a chosen day of the month (or "last day", for a month-end duty) — that produces ordinary tasks by itself, entered once, "like the alarms on a phone" (the owner's phrase from the design). Design: `docs/superpowers/specs/2026-08-15-recurring-tasks-design.md`.

**The load-bearing design fact: an occurrence is an ORDINARY row in `tasks`, not a virtual computation and not a flagged template task.** This is why the feature touches almost nothing else — Upcoming, the calendar grid, the daily summary, calendar sync and the AI agent's day view/`search_tasks` all already read `tasks`, so every one of them sees an occurrence with zero code change. The generator itself is a small pure module, `recurrence.py` (no I/O, the same shape as `hostaway_threading.py`), doing only "a rule plus a date range → a list of dates".

**A rolling ~14-day window of real rows** is kept materialized ahead by the existing per-user ~2-minute scheduler tick — the same tick Hostaway's reply-polling and reminders already run inside — plus synchronously the moment a rule is created, edited or approved, so the user sees tasks appear immediately rather than waiting for the next tick. The actual duplicate guard is `UNIQUE (recurrence_rule_id, occurrence_date)` **in the database**, not a check in Python, because the tick runs every two minutes for every user and any crash, retry or overlapping run has to stay harmless with nobody watching it happen.

**`occurrence_date` is a separate column from `due_date`, and this is the subtlest point in the design.** The two start equal, but dragging an occurrence to another day (the existing reschedule flow) changes only `due_date`. Had the uniqueness key been `due_date`, the next tick would see the original day "missing" and recreate it — a duplicate on every single reschedule. `occurrence_date` is written once at creation and never changes again.

**An occurrence stops being open in exactly three ways, and each is its own column, deliberately not `is_rejected`:** completed, same as any task; `missed_at` — it outlived its rule's one day of grace, so on the second day after it was due it closes itself and leaves the visible lists, recorded rather than deleted, which is what lets "was Monday's check done?" have an answer; and `cancelled_at` — a human deleted this one occurrence, and the row has to survive precisely so the generator does not see that day as ungenerated and recreate it within about two minutes. `is_rejected` was rejected for all three: it means "the user rejected the AI's suggestion" and is preserved on purpose to feed the AI learning loop, and filling it with hundreds of auto-closed or auto-cancelled rows the AI never proposed would corrupt that signal.

**Editing a rule takes effect from tomorrow, never retroactively** — today's occurrence may already be half-done or already have rung, so it is left alone; edit it as the ordinary task it is if it needs to change today. Two things deliberately survive a rule edit: already-completed occurrences, and any occurrence the user has already moved by hand (`due_date != occurrence_date`) — someone who deliberately shifted next Tuesday's task should not lose that just because the rule's time changed. **Pausing a rule (the off switch) removes its already-generated future occurrences immediately** — "off" means stopped now, not "no new ones after the fortnight already generated runs out" — while today's occurrence and all history stay; turning it back on regenerates the window. Deleting a rule removes every open occurrence, past and future, and keeps completed and missed ones as ordinary tasks (`ON DELETE SET NULL` on `recurrence_rule_id`) — history survives the rule.

**Reached from Settings → Recurrences** (a `SettingsRow` exactly like Hostaway, Notifications and Calendar), which lists every rule with an on/off switch and opens a form for a new one. Everything an ordinary task has — name, description, category (never `Hostaway`, which belongs to that integration's own escalation logic), priority, checklist, reminder bell, calendar toggle — is inherited by every occurrence the rule produces.

**A task can also be made to repeat from the task itself (2026-08-17)**, which is how most of them are: from the `⋯` menu (shared by the list row and the detail sheet) or from the "Repeat — Never" row in `TaskDetailSheet`, beside the reminder and calendar switches. The form opens prefilled from the task, with the weekdays defaulting to the ONE day it already falls on rather than Mon-Fri — "repeat this" said about a Tuesday task almost always means every Tuesday, and five pre-armed days invites saving four commitments nobody asked for.

**The task the user was looking at BECOMES the rule's first occurrence** rather than being duplicated beside one. `POST /recurrences` takes an optional `adopt_task_id`; the named task is given `recurrence_rule_id` and `occurrence_date`, and since the generator skips any `occurrence_date` already on disk, that day is not generated again. The order — adopt, then materialize — is the whole mechanism. Adoption links and does not edit: the rule's time, priority and category are NOT written over the task's, because the user asked for this task to repeat, not to be replaced by the template. A task that already belongs to a rule is refused (422) and one that is not yours is a 404, both resolved before the rule row is written so a failed adoption cannot leave an orphan rule firing every morning. A closed task (completed, rejected, missed, cancelled) is deliberately not adopted — the rule simply starts fresh — and an undated task is pinned to the rule's `starts_on`.

The ↻ marker on a generated task's row is a **button** reading "Repeats · Mon-Fri", opening that rule for editing. (It was a non-interactive glyph until 2026-08-17, on the grounds that making it a link meant threading a callback through three components; the answer turned out to be a context, `RecurrenceProvider`, which holds the single copy of the rules and hosts the editor modal above the list — a modal rendered inside a row would be clipped by the same `overflow-hidden` that already forced `TaskMenu` into a portal.) When the rules have not loaded, the badge falls back to the bare word rather than vanishing, and the detail sheet says "Repeats" instead of the pattern — never "Never", which would be a lie about the user's own data.

**Scope OUT**: streaks or statistics ("26 of 30 this month") — the data is stored so this can be added later without a rewrite; assignment to a colleague — a rule belongs to the user who made it, and `assigned_to` is one column away when it is wanted; "every 3 days" or "every second Tuesday" — only a weekday set or a day-of-month; end times — a recurrence has a start time only, like an alarm, never a duration; and natural-language creation ("every Monday, gym at 7"), which is Slice 2 — the AI extractor learning a recurrence shape — and **has not started**. The chat agent and the per-card agent are both untouched by Slice 1.

**Verified, and what is not.** 209 unit tests cover the generator (weekday and monthly expansion, month-end clamping including `-1` for last-day, the grace boundary on both sides, horizon edges) and, against a fake repository, the service-level behaviour — running the generator twice creates nothing the second time, a rescheduled occurrence is not regenerated, a rule edit preserves completed and hand-moved occurrences, deleting a rule keeps history and removes open rows, and an adopted task's own day is not generated a second time.

**The owner ran the six-step browser walkthrough on 2026-08-17 and reported it passed**: the Recurrences screen, the New/Edit form, generation into Today/Upcoming/the calendar, pause, resume and delete. That is the feature working in front of a person.

What is still unwitnessed: a rule surviving a real midnight on the scheduler's own tick, a missed occurrence closing itself unattended on day two, a reminder firing for a rule-generated row, and every pixel of the make-this-repeat path added later the same day — the ⋯ entry, the detail-sheet row, the clickable badge, and above all the claim that adoption leaves exactly one copy of the task on today's list. See CURRENT_TASK.md.

### Feature: AI agent (read) — question answering over your tasks
`agent_engine.ask_agent(question, user_id, conversation_id=None)` loads only that user's tasks into RAM, then exposes `search_tasks` (filters by date/category/priority/keyword, fuzzy Greek↔Latin, caps 30 results, truncates descriptions) and `get_task_details`. Only the filtered tool results reach the LLM (cost control); the raw task list never does. Manual tool-call loop (AFC disabled) sums token usage across rounds. Task loading/filtering is still fully stateless every single request; a bounded conversation history of past questions/answers (never tool results) is now replayed ahead of the current turn — see "AI agent (memory)" below. Directives: CONFIDENTIALITY (won't reveal its instructions), DATA-VS-INSTRUCTIONS (tool results incl. Hostaway text are data, not commands), TIME AWARENESS, DATE RESOLUTION. `search_tasks` results are sorted chronologically (due_date, then due_time, then priority) BEFORE the 30-result cap is applied, so the cap keeps the soonest matches rather than an arbitrary subset (see DECISIONS.md). The LATEST (current) user turn — not necessarily the first, now that a bounded conversation history may be replayed ahead of it (see "AI agent (memory)" below) — also carries a **pre-loaded day view** (`agent_tools.build_day_view`) — a compact, pre-sorted table of every OPEN task that is overdue or due today, plus anything PENDING APPROVAL (created but not yet approved — usually AI extraction or a Hostaway webhook task) that is due today or already late. It is injected on EVERY request, unconditionally (no pattern-matching the question — a missed injection costs a whole extra round, an unneeded one costs a few hundred tokens). This is what lets "what do I have today?" and "what's overdue?" resolve in a single round with ZERO tool calls: the system instruction tells the agent the view is COMPLETE for those two scopes and it must answer directly from it, but for any other scope (tomorrow, a weekday, a category/keyword filter, completed tasks, a specific date) it MUST still call search_tasks — the day view says nothing about any day other than today, and the agent is told never to extrapolate from it. Today's timed tasks show pre-computed passed/upcoming; each row's `record_id` doubles as a valid source for a write's `record_id` (see "AI agent (write)" below), which is what lets "mark today's task X complete" skip the lookup round too. All three sections are CAPPED (overdue 10, today 15, pending 5) with a "(+N more ...)" overflow line — the day view lives in `contents[0]` and is therefore re-sent on every round, so an uncapped section would put unbounded tokens into every request. This REPLACES the earlier `overdue_count` mechanism entirely (removed, along with its own system-instruction section) — two mechanisms answering the same question is exactly the kind of thing that produces contradictory instructions. "Overdue" is still defined as strictly BEFORE today — a task due today is not overdue, it belongs to today. A bare weekday name ("Τετάρτη", "Monday") resolves to the UPCOMING occurrence by reading it straight off a `[Next 7 days]` date-lookup map injected into the user's turn, rather than the model computing it; that map is a lookup table only, never a search range. When a date-filtered search_tasks call finds zero matches, the result carries `no_matches_hint` (the nearest dates that DO have open tasks) so the agent can suggest a real alternative instead of blindly retrying adjacent dates round after round. If the tool-call loop hits its round ceiling (`MAX_TOOL_ROUNDS`, now 4) without a final answer, it no longer raises an error to the user — one last tool-less round forces an answer from whatever was already found, which the logs record as `outcome=max_rounds_recovered`. `search_tasks` filters are only ever populated from what the user explicitly asked for; an absent time reference means an unbounded date search (both `date_from`/`date_to` empty), not a default window — the agent must never invent a category, priority, keyword, or date range the user didn't actually give it.

**Retrieval and self-correction (2026-08-06 overhaul — see DECISIONS.md).** `search_tasks` now recovers from its own near-misses in-process instead of asking the model to search again, because a model retry costs a whole round (~3.300 tokens) and an in-memory re-scan costs microseconds. Three matching tiers, each consulted only if the previous found nothing: exact substring → any 4+ char WORD of a multi-word keyword (a multi-word keyword can essentially never match as one literal string, even when every word of it is present) → 5-char accent-folded word STEMS, which is how Greek inflection is bridged ("οδοντίατρος" finds "Ραντεβού οδοντιάτρου", previously invisible). A keyword that finds nothing open is automatically retried against completed tasks, so an already-done task is reported as done rather than as missing. `undated_only` answers "what has no deadline?", which previously had no expressible form at all and made the model hunt for it category by category. Results carry their own instructions next to the data — `truncated_hint`, `undated_hint`, `fuzzy_keyword_note`, `completed_only_note`, and `over_filtered_hint`, which fires when a multi-filter search returns 0 and also hands back `relaxed_matches`: the actual rows the same search finds with filters relaxed, so a search narrowed by a filter the user never asked for cannot be reported as "you have none". The user also SEES the filters of every search under the answer (see "AI agent (write)" frontend notes below) — the one check that isn't the agent policing itself.

### Feature: AI agent (write) — propose-then-confirm — Phase 1 — **SHIPPED ✅**
The agent never executes writes directly. `agent_tools.build_write_proposal_tools(proposed_actions, available_tasks)` gives the agent three tools — `propose_complete_task`, `propose_update_task`, `propose_create_task` — which only VALIDATE and append a structured proposal dict (referencing the user's own loaded tasks). A record_id may come from EITHER a tool result (search_tasks/get_task_details) OR the PRE-LOADED day view now injected into the latest user turn (see "AI agent (memory)" — earlier, replayed turns never carry their own day view) — both are drawn from the same user-scoped `cached_tasks` list in the same request, so either is a valid source; what's actually forbidden is inventing, guessing, or modifying one. A `[refs: name=id]` line replayed from an earlier answer in the same conversation is a third valid source, subject to the same never-invent rule — see "AI agent (memory)". This is also what lets a write on a task already visible in the day view (e.g. "mark today's task X complete") skip the lookup round entirely. `agent_engine.ask_agent(question, user_id, conversation_id=None)` returns `{answer, proposed_actions, conversation_id}`. `POST /agent/query` accepts an optional `conversation_id` and returns that same shape. The system instruction (in `agent_tools.build_system_instruction`) tells the agent to always present a proposal as pending confirmation, never as already done. Manually verified end-to-end logged-in against live Supabase data (2026-08-01): complete/update/create proposals, individual confirm, local-only cancel, ephemeral cards, Inbox landing for created tasks, and two-account isolation all behave as specified.
On Confirm, a SEPARATE endpoint `POST /agent/confirm-action` executes the real write — this is the security boundary, not the UI or the propose tools. It re-validates from scratch: allowed action types (`complete_task`/`update_task`/`create_task`), the field whitelist `agent_tools.AGENT_WRITABLE_FIELDS` = {due_date, due_time, priority, category, task_name, description}, enum values (category/priority), date/time formats, and user_id scoping (inherited from `TaskService`'s existing user-scoped methods — a record_id belonging to another user simply matches no row). A `create_task` confirmation calls `service.create_task_manual(user_id, fields, approval_status=False)` — the new `approval_status` param (default `True`, unchanged for the normal manual-create path) is what makes an agent-created task land in the **Inbox for approval** instead of appearing directly in the task list (the "hybrid" behavior). Scope for Phase 1: complete/update/create only. OUT of scope: delete tasks, any Google Calendar event operations (Phase 2 — see BACKLOG.md).

**Frontend UI behaviour** (`AgentChatModal.jsx`): each proposed action renders as its own confirmation card directly under the assistant reply it came from (stored as `message.actions`, so cards stay attached to their reply as the chat scrolls). There is **no "Confirm all"** — every card is confirmed individually, deliberately, so one write can't accidentally drag another along with it. Each card has its own idle → pending → done | cancelled | error state; confirming or cancelling one card never affects any other card in the same reply, and a card that's already `done`/`cancelled` can't be confirmed again (guarded against double-click too). Confirm calls `confirmAgentAction(action)` and, on success, folds the returned task into the existing `tasks` state the same way a normal task edit/create already does (no extra fetch) and replaces the card with a compact line showing the server's message. Cancel is **purely local** — it greys out the card and makes no server call; nothing changes. A `create_task` card explicitly tells the user the new task will land in the Inbox for their approval. Un-confirmed cards are **ephemeral**: they live only in the current chat session's React state — resetting the chat or reloading the page discards them and nothing was ever written.

**Search transparency (2026-08-06).** Under every assistant reply, a muted `SearchTrace` line lists the filters of each search the agent ran and how many matched — "Έψαξα: με «ψώνια» · 1 βρέθηκαν", or "Έψαξα: σε Business, από 2026-08-06 έως 2026-08-13 · 2 βρέθηκαν", or "Έψαξα: όλα τα ανοιχτά" when a search carried no filters. Only filters actually passed are shown. This exists because the agent was observed narrowing a search with a category and a date the user never mentioned and then reporting "you have none" over it, entirely invisibly; the tool-level guards try to prevent that, but only the user knows what they meant, so this is the backstop (see DECISIONS.md). It shares the propose-then-confirm philosophy: show the machine's intent before it matters. Fully translated (`agent.searched_*` keys, EN/EL).

**Pending-approval writes are refused (2026-08-06).** A task still awaiting approval in the Inbox cannot be completed or updated by the agent: `propose_complete_task`/`propose_update_task` return an error the agent explains to the user, and `/agent/confirm-action` independently re-checks and returns 409. Previously this rule lived ONLY as one line in the system instruction, so nothing in the codebase would have stopped an approval bypass if the model dropped that line. Also, `propose_update_task` now drops any field whose value already matches the task, so a confirmation card shows only what genuinely changes (the model was observed re-sending all six fields to change one date).

**A follow-up write must target a task the conversation actually named (2026-08-07).** The worst agent bug found so far: after asking "πότε είναι το ραντεβού στον οδοντίατρο;", the follow-up "άλλαξέ το για την Παρασκευή" produced an update proposal against **the first row of the day view** — a task the user had never mentioned — in 4 of 6 repetitions. Confirming that card edits the wrong task. Two guards now prevent it: `propose_complete_task`/`propose_update_task` refuse a target that is neither a record_id this conversation has already surfaced nor a task named in the current question, and the tasks the conversation HAS discussed are now injected into the current user turn (above the day view) rather than left trailing an older reply where the model was demonstrably not reading them. Separately, `propose_update_task` refuses a `description`/`task_name` copied character-for-character from a different task — the next thing the model did once it started hitting the right task was fill the fields with the wrong one's data. Measured after: 0 wrong writes in 5, and the confirmation card now carries only the field that actually changes. Cost: a blocked contaminated proposal takes the run from 2 rounds to 4 (see DECISIONS.md). The user-visible backstop is unchanged and still matters — the agent names the task it resolved to, so a wrong guess is readable before it is confirmed.

### Feature: AI agent (memory) — bounded conversation history — SHIPPED ✅
`POST /agent/query` accepts an optional `conversation_id` and always returns one (minted server-side via `uuid4` when absent). The backend reconstructs history itself from the `agent_runs` table via `repository.get_recent_agent_runs(user_id, conversation_id, limit=agent_tools.HISTORY_MAX_PAIRS)` — the client never sends history, only the id, so it cannot inflate the prompt or the bill no matter what it sends. The last `HISTORY_MAX_PAIRS` (4) question/answer pairs (8 messages) are replayed ahead of the current turn via `agent_tools.build_history_contents`; ONLY the stored `question` and `answer` columns are ever replayed — questions and final answers ONLY, never raw tool results — which is what keeps this cheap (a tool result is already the expensive, re-sent-every-round part of a single request — see DECISIONS.md — so replaying it across turns too would compound that same cost). Each replayed message is independently truncated to `HISTORY_MSG_MAX_CHARS` (500 chars). An assistant turn whose run touched 5 or fewer distinct tasks (via `search_tasks`/`get_task_details` results — NOT the day view, which is re-injected fresh every request and never needs remembering) carries a compact trailing `[refs: task_name=record_id; ...]` line, capped at `HISTORY_MAX_REFS` (5) entries; a run touching MORE than 5 tasks stores `refs=[]` instead of an arbitrary subset, so a follow-up like "change it to Friday" either resolves straight from a remembered id or correctly falls back to a fresh `search_tasks` call rather than guessing. Refs are the ONLY record_id source history contributes — history resolves REFERENCES ONLY and never supplies task facts: the CONVERSATION HISTORY system-instruction directive is explicit that history itself may be stale (minutes or hours old) and must never answer a task-facts question directly; those always come from the fresh day view or a fresh tool call in the current turn. Ambiguous follow-ups ("set it to 5") are clarified, never guessed — a guessed value could land on a confirmation card the user accepts without reading (see DECISIONS.md).
**Lifecycle**: a conversation lives exactly as long as `AgentChatModal.jsx` stays open. Closing it (✕) or tapping "New conversation" resets `conversationId` to null and clears both `messages` and any un-confirmed proposal cards — cards were already ephemeral (chat-session React state only, per "AI agent (write)" above); this just adds two more ways that state gets dropped, and un-confirmed cards are never restored. The chat always opens clean: no restored history, and THREE read-only starter suggestion chips ("What do I have today?", "What's overdue?", "What's my week look like?" — translated EN/EL via react-i18next) are shown above the input while `messages` is empty; tapping one fills the input and sends it immediately, and the chips disappear after the first message. Deliberately NO "Add a task" chip — creating a task through the agent costs a proposal round for something the normal add-task form does for zero tokens (see DECISIONS.md).
**Scope OUT**: browsing or resuming past conversations in the UI (`agent_runs` already stores everything needed for this — see BACKLOG.md), cross-device conversation resume, summarizing older turns instead of just dropping them past the 4-pair window, and replaying tool results (deliberately, for cost — see above).

**Developer diagnostics** (not user-facing): every `ask_agent` run — success or failure — is persisted as one row in `agent_runs` (see DATABASE_SCHEMA.md), capturing the exact first-turn prompt text, every round's tool calls, and the same totals/outcome already in the console `[SUMMARY]` line, so a verification pass survives Render's ephemeral application logs and becomes a SQL query instead. The SAME row is also the memory source replayed above — one table, two uses (see DECISIONS.md). A question may start with a `#label ` prefix (e.g. `#t3 what do I have today?`) to tag that run for later lookup by `test_label`; `agent_tools.strip_test_label` strips it before the model ever sees it, and it is never replayed as part of conversation history either. `agent_runs` is diagnostic + memory only and is never summed for usage or cost — see DECISIONS.md.

### Feature: AI agent (history) — what you asked, and what you decided (2026-08-23) — **VERIFIED RUNNING end to end (2026-08-24)**

**Resume was deliberately dropped.** Of the three things a history could do — re-read, resume, audit — resuming is the only one that re-sends the old messages to the model and is paid for again on every turn. The owner chose re-read + audit and refused resume on that basis (2026-08-23).

**The stated premise was wrong, and finding that out was most of the work.** The backlog said `agent_runs` "already stores everything needed". It stores what the agent **proposed**. Nothing stored what the user **decided**: Confirm executed the write and left no trace it came from the agent — the single exception being `complete_task`, which sets `completed_source = 'agent'` — and **Cancel never reached the server at all**, being purely local state in `AgentChatModal.jsx`. Walking away from a card is a different fact from refusing it, and reporting it as a refusal would poison the very signal the table exists to collect. The screen colours confirmed as success, cancelled as danger, and leaves undecided neutral: not deciding is not a failure.

**Two facts about the data, measured 2026-08-23 rather than assumed.** 282 of the 348 rows in `agent_runs` were tagged development test runs, so `test_label is null` is applied in the query itself — without it the screen shows the developer's noise instead of the user's work. **VERIFIED RUNNING (2026-08-24)**, against the `tasks` and `agent_action_decisions` rows rather than trusted. Preference is stored in `localStorage` under `app_theme`, matching the Language switcher rather than the backend's `app_settings`: it is a per-device setting, and a phone in bed and a laptop at a desk want different answers. No new tables, no endpoints, no backend change at all.

Three things ride along because the app can now disagree with the OS: the `theme-color` meta tags are rewritten by JS (their media queries follow the OS, which would leave dark phone chrome around a deliberately light app), `color-scheme` is declared so native controls like the daily-summary time picker follow too, and Tailwind's `dark:` variant is repointed at the same attribute — it has no users today, but two stray `dark:` classes had already caused exactly this bug once (FRONTEND_1ST_POLISH.md §5).

**Verified headlessly, not in a browser** (`npm run check` → `scripts/theme.test.mjs`): stored preference beats the OS in both directions, choice persists, OS changes are followed under "System" and ignored otherwise, junk stored values degrade to System, and `index.html`'s inline pre-paint script is compared against the module across every (preference × OS) pair. Both new checks were fault-injected to confirm they fail when they should. The Settings row itself — three buttons in the same pattern as the Language row — was **checked in a running browser by the owner** before this shipped; the automated side has never seen it rendered, so the tests above are the thing that will catch a regression, not the thing that proved it worked.

### Feature: Browse rebuilt — soft delete and a History tab (2026-09-04) — **SHIPPED, partly watched**
The owner's complaint was the screen, not the data: three separate rows of controls before you saw one task, no priority filter (every other screen has one), and no way to look at what had already happened.

**Two tabs, because they are two questions.** «Ενεργά» asks *what do I do* → Κατηγορία / Προτεραιότητα / Ταξινόμηση, one row. «Ιστορικό» asks *what happened* → Τι / Πότε, grouped by day. One screen carrying both sets is what the old one was. Not a fifth bottom-nav tab: that nav is deliberately four wide because at a fifth of a phone screen "Εισερχόμενα" was being clipped. Category counts moved into the menu («Ακίνητα (18)») and appear on Ενεργά only — a count of live work above a list of finished work answers the other tab's question.

**Deleting stopped destroying the row.** `deleted_at` (migration `2026-09-04-task-soft-delete.sql`, applied and read back: total 325, deleted 0). `repository.delete_task` → `soft_delete_task`, renamed so a missed call site raises rather than silently keeping the old behaviour; `restore_task` clears it, behind `POST /tasks/{id}/restore`. The rule went into `agent_tools.is_open_task` and `taskDisplay.isVisibleTask` and **nowhere else** — those two are what keep a deleted task out of the agent, the day view, the reminders, the Hostaway escalation query, Today, the Calendar, Upcoming and the Inbox simultaneously.

**Everything that left the live lists is in History**, in four buckets: ολοκληρωμένα, διαγραμμένα (both `deleted_at` and a recurrence's `cancelled_at` — the same act to the person who pressed Delete), χαμένες επαναλήψεις, απορρίψεις AI. `missed_at` and `cancelled_at` had been written correctly for weeks and were **visible nowhere in the app**; the old code said so in a comment ("there is no history view yet").

**Two things it refuses to smooth over.** A completion from before `completed_at` existed (2026-08-13) says «η ώρα δεν καταγράφηκε» rather than printing an hour that would read as fact. An entry with no date at all is excluded from every range except «Όλο το αρχείο», because it cannot honestly answer "in the last 7 days". Both follow the migrations' own rule: NULL, never a backfilled guess.

**Accepted hole, decided with the owner**: restore does not recreate a deleted Google Calendar event — that event is gone from the calendar and Google is outside this database. The dead link is cleared and the toast says so instead of reporting a bare success. Asserted by `test_restoring_an_app_origin_task_clears_the_dead_calendar_link` so it cannot be quietly closed or quietly forgotten. Restore has **no time limit**: nothing purges rows, so a cutoff would be code whose only job is to refuse something that works.

**A regression this feature caused, found by the owner within minutes of the deploy.** Moving completed and rejected tasks into History removed the two Browse toggles that used to show them as ordinary cards — where the circle un-completed them and the ⋯ menu un-rejected them — and the first version of History put a button on deleted rows only. A task ticked off by accident had no way back. Fixed in `33ab9e7`: completed rows offer **Ξανάνοιγμα**, rejected rows **Αναίρεση** (which returns the suggestion to the **Inbox**, not to Ενεργά — it was never an approved task), both through the same `onTaskUpdate` every other screen uses. Missed occurrences deliberately get no button and are the one state where nothing was taken away.

**Two older bugs fixed on the way.** Browse's "Εμφάνιση απορριφθέντων" toggle bypassed `isVisibleTask`, so a soft-deleted task would have shown in the live list. And **"Νεότερα"/"Παλαιότερα" were sorting nothing**: `TaskList` ordered by `created_time`, the Airtable-era column that is popped from both the insert and the update path and has no database default — it has never been written. `created_at` is now surfaced on `TaskRecord` (read-only, popped on write in both paths) and both the sort and History read it.
