- **Task report export (Excel / PDF)** — e.g. "κάνε μου report με όλα τα business tasks του έτους". Design already thought through (2026-08-02), parked for later:
  - **Core principle**: the file is generated ENTIRELY in Python; the agent's only job is translating natural language into parameters (`date_from`, `date_to`, `category`, `include_completed`) — roughly 30 output tokens. Task rows never enter the model's context, so 500 tasks cost the same as 5, `MAX_SEARCH_RESULTS = 30` does not apply (it is a token guard and there are no tokens here), descriptions are not truncated to 100 chars, and the totals are arithmetically correct because Python counts them, not the LLM.
  - **Excel first, not PDF.** PDF has a concrete Greek-text trap: `reportlab`'s default fonts (Helvetica/Times) have no Greek glyphs, so it needs an embedded TTF (DejaVuSans/Noto, ~700KB committed to the repo); `weasyprint` needs cairo/pango system libs, awkward on Render. Excel has none of that (UTF-8 is fine) and is more useful anyway — the owner can filter/sort/pivot.
  - **Dependency needed**: nothing suitable is installed today (checked: no openpyxl / xlsxwriter / pandas / reportlab / weasyprint). `xlsxwriter` (zero transitive deps, write-only) or `openpyxl`. NOTE: `requirements.txt` is UTF-16LE with BOM — preserve the encoding when adding the line.
  - **Fits the existing propose-then-confirm plumbing**: a `propose_report(...)` tool appending `type: "report"` to `proposed_actions`, rendered as a card with a "Download Excel" button instead of Confirm, hitting a dedicated user-scoped endpoint that streams the file. Reuses the cards, the proposed_actions flow, and the server-side re-validation pattern.
  - **Open question — does this need the agent at all?** A "Reports" button in the UI with category + date-range pickers costs ZERO tokens forever and is more discoverable; an agent tool costs ~150-250 tokens on EVERY request whether used or not (compare: the three `propose_*` tools measured at 762). Suggested order: build the endpoint + UI button first (that's where the actual work is), then decide separately whether the natural-language layer earns its per-round cost.

- **Hostaway encryption key: rotation, and one key for everyone (2026-08-14)** — two accepted weaknesses of the `HOSTAWAY_ENCRYPTION_KEY` design, both fine for one business and neither fine indefinitely (see DECISIONS.md). **Rotation**: if the key leaks, the correct response is a new key plus re-encrypting every `hostaway_connections` row, and nothing does that today — the key cannot currently be changed without breaking every stored secret, which also means a leak has no remediation short of every user reconnecting by hand. A small script (decrypt with old, encrypt with new, in one transaction) closes it. **One key for all**: the fifteen colleagues' secrets all encrypt under the same key, so it is a single point of compromise for the whole team; per-user keys, or a KMS, would be better and considerably more complex. Neither is urgent; both should be revisited before a second business connects.

- **Sync into OUR OWN calendar instead of `primary` (2026-09-04)** — the structural fix the big apps already made, and the root of two problems we patched at the leaves. Todoist creates a calendar named "Todoist" and syncs into that; turning sync off then deletes those events safely, because nothing of the user's own is in there ([their docs](https://www.todoist.com/help/articles/use-the-calendar-integration-rCqwLCt3G)). We write into the user's `primary`, which is why turning a task's switch off is dangerous enough to need a confirmation, and why the pull drags 90 days of the owner's personal life across every tick. Not small: an existing event per task already lives in `primary`, and the "show my Google events in the app" feature still has to read `primary` regardless — so this is a new calendar for WRITES only, plus a decision about what happens to the events already out there.
- **The syncToken is never stored, so every pull is a bootstrap (2026-09-04)** — `google_calendar_connections.calendar_sync_token` is empty and stays empty: the bootstrap request sends `timeMin` + `orderBy`, and Google does not return a `nextSyncToken` for a request carrying those. So every ~2 minutes the app re-reads 90 days of the primary calendar. Now that the pull writes only on real change this costs bandwidth rather than database writes, which is why it is parked rather than urgent. **When it is fixed, one thing must be fixed with it**: an incremental sync also reports DELETED events, so an event we deleted on purpose (the item above) would come back as `status: cancelled` and `mark_task_calendar_deleted` would append "⚠️ Διαγράφηκε το συνδεδεμένο event" to a live task — a warning about something the user themselves asked for. Cannot happen today; would be immediate the day the token works.
- **Let Google knock instead of asking it every two minutes (2026-09-04) — the owner asked for this explicitly, so it is a wish, not a note.** Google Calendar can push a notification to a URL when a calendar changes (a "watch channel"), which is what the Hostaway integration already gets for incoming messages.
